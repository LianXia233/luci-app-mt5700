# v1.14.17

> 上一版：v1.14.16（自动推送总开关 + 短信/来电实时推送 + 信号定时巡检）
> 本版聚焦三件事：**时间口径统一为系统时区**、**巡检推送携带完整信号评估**、**短信中心会话内收发分区**。

## 一、时间口径统一为系统时区（默认北京时间）

### 现象

服务日志与推送正文里的时间**整体早 8 小时**。同一个时刻，SSH 里 `date` 显示 `CST`，服务日志却是 UTC。

### 根因（两层，缺一不可）

1. **`TZ` 环境变量传不到守护进程** —— 它只由 `/etc/profile` 为**登录 shell** 导出，procd 拉起的进程拿不到；`/etc/profile` 里的 `export TZ` 对 `procd` 完全无效。
2. **本固件不打包 tzdata** —— 实机 `/usr/share/zoneinfo` 不存在，musl 的 `localtime_r` 在无 `TZ` 时**不报错、静默退化成 UTC**。于是「没有报错」掩盖了「时间全错」。

### 修复

新增 `crate::localtime` 模块，三级回退解析本地偏移：

| 顺序 | 来源 | 说明 |
|:--|:--|:--|
| 1 | `TZ` 环境变量 | 显式注入时最高优先 |
| 2 | `/etc/TZ` | 系统时区派生的 POSIX TZ 串（如 `CST-8`） |
| 3 | `uci -q get system.@system[0].timezone` | LuCI「系统 → 时间同步 → 时区」写入的值 |
| 4 | `CST-8` | 以上都没有时回落**北京时间 UTC+08:00** |

`/etc/init.d/at-webserver` 按**完全相同的顺序**取值，并通过 `procd_set_param env TZ=...` 注入给后端 —— 两侧同序，保证服务内外口径一致。

后端所有 `chrono::Local` 调用点改走 `localtime::now()` / `chrono::DateTime<localtime::Tz>`：

- `pdu.rs` —— 短信时间戳解码；
- `logger.rs` —— 通知日志时间戳；
- `schedule.rs` / `schedconfig.rs` —— 定时锁频判定与「下一次切换时刻」。

覆盖到 UI 的范围：通知日志时间戳、推送正文里的 `{time}`、短信中心每条短信的时刻、定时锁频的下一次切换时刻。

### 启动日志

```
时区: CST-8 → UTC+08:00
```

或（未配置时）：

```
时区: 未配置时区，使用默认北京时间 UTC+08:00（默认）
```

让口径在日志里**可见**，而不是只能靠猜。

### 一个容易踩的坑

POSIX TZ 串的**符号与直觉相反**：`CST-8` 表示 **UTC+8**（POSIX 中符号代表「本地时间 = UTC − 偏移」）。写成 `CST+8` 会得到 UTC−8，比不设时区还要糟。

### 验证

模拟环境两段断言：

1. **不提供任何时区配置**时，通知时间戳 == `Date.now() + 8h` —— 防止「默认值不是北京时间」；
2. 注入 `system.@system[0].timezone=UTC0` 后重启，时间戳整体回落 UTC —— 防止「把默认值写死、无视系统设置」。

## 二、巡检推送携带完整射频信号评估

原巡检推送只带一个 RSRP 数值，不足以判断链路是否真的可用。本版把网页「射频信号质量」卡片的评估逻辑**完整搬到推送侧**：

```
网络能力优秀
信号与频段带宽俱佳，适合高清视频及大文件下载
信号强度  优秀
信号质量  优秀
信噪比    优秀
综合      优秀
RSRP 信号强度  基准 ≥ -80    -63 dBm    极佳  覆盖极佳
RSRQ 信号质量  基准 ≥ -10    -10 dB     极佳  纯净通畅
SINR 信噪比    基准 ≥ 20     28 dB      极速阶数
SIGNAL 综合信号 满分 100%    100 %      极佳  满格服务
```

- 新增 `signalgrade` 模块承载评估规则；
- `urc::parse_signal_reading()` 与评估模块**共用同一套换算与分级**，避免同一组读数在网页与推送里给出两个不同结论。

## 三、短信中心：会话内收发分区排列

同一联系人的对话改为**两块分区**渲染：

- **上区**只放收到的短信，**下区**只放发出的短信，各自按时间升序；
- 中间以分隔标题区分（「收到 N 条」/「发出 N 条」）；
- 会话列表按最近联系时间**倒序**。

原来的收发交错排列会让「哪条是自己发的」难以辨认，尤其在群发场景下会与对面的消息挤在一起。

### 顺带修掉两个真实缺陷

| 缺陷 | 根因 | 修复 |
|:--|:--|:--|
| 存储用量永远显示 **0 / 0** | 前端请求私有命令 `AT^CPMS?`，模组回 `^CPMS: "SM",<used>,<total>,...`，而原正则只匹配标准前缀 `+CPMS` | 改为 `[\^+]CPMS` |
| 号码三处口径不一致（推送 `8613800138000` / 来电 `+8613800138000` / 界面 `13800138000`） | 各链路各自处理，没有统一归一 | 新增 `notify::normalize_phone_number()`，与前端 `Parse.normalizePhoneNumber` 同规则（剥 `+`、去国家码 `86`、只留数字） |

### 时间诚实的三个档位

发出短信的 PDU 里**没有发送时刻**（SMS-SUBMIT 只有 TP-VP 有效期），因此界面按证据强度如实标注：

- 只有相对有效期 → 标「时间未知」；
- 有绝对有效期 → 标「（有效期时间，非发送时刻）」；
- 收到短信有 TP-SCTS → 正常显示时刻。

不编造时间。

新增 `tests/mock-modem/` 离线模拟链路，**不需要实机即可回归**：


| 文件 | 作用 |
|:--|:--|

### 附带产物：PDU 夹具的一个规范细节修正

`3GPP TS 23.040` 里**地址长度字节是普通二进制（半字节计数），不是 BCD**；只有 TP-SCTS / 绝对 TP-VP 的时间字段才是交换半字节 BCD。夹具最初把地址长度也写成 BCD，导致首个 PDU 解析整体失败。这类错误在实机上表现为「短信列表空白」，排查成本很高。

## 六、安全约束：IMEI 与恢复出厂设置不可触碰

本轮测试全程遵守「**IMEI 与恢复出厂设置相关一律不碰**」这条硬约束，并落地**三层护栏**：

| 层 | 位置 | 行为 |
|:--|:--|:--|
| 1 | mock 模组 `FORBIDDEN` 命令表 | 命中 IMEI/序列号写入、恢复出厂、复位即回 `ERROR` 并留日志 |
| 2 | 测试脚本 `assertSafe()` | 下发**前**拦截，命中即抛错终止 |
| 3 | 事后 `auditModemCommands()` | 扫描整轮测试的全部下发命令 |

当前审计结果：

```
扫描下发命令 23 条，危险命令 0 条（被拒 3 次，均为护栏自检）
```

只读命令 `AT+CGSN`（读 IMEI）/ `ATI` 保留，后端设备识别不受影响。

## 升级方式

```sh
# apk 系统（OpenWrt 25.x / ImmortalWrt SNAPSHOT）
apk add --allow-untrusted ./<ARCH>-luci-app-mt5700-1.14.17-r1.apk

# opkg 系统（OpenWrt 24.10 及更早）
opkg install ./<ARCH>-luci-app-mt5700_1.14.17_<ARCH>.ipk
```

升级后建议重启服务并清理 LuCI 前端缓存：

```sh
/etc/init.d/at-webserver restart
rm -rf /tmp/luci-modulecache /tmp/luci-indexcache
```
