# v1.14.19

> 本版把「测试推送」从一个按钮拆成两种粒度：**通道连通性**与**事件类型**。

---

## 一、为什么需要「按事件类型测试」

原先只有「发送测试通知」一个按钮，它只回答一个问题：**这条通道到底通不通**。

它发的是固定文案、不经过事件链路，于是有三件事验证不了：

- 换过的短信/来电文案**长什么样**；
- 短信是不是真的**实时直发**、不等 `notify_interval` 合并窗口；
- 尤其是短信与来电本身 —— 这两类**只能由模组 URC 触发**（`+CMTI` / `+CLIP` / `^CEND`），要验证就得真的收一条短信、接一通电话。

在实机上部署完新文案后，用户能做的只有「等一条短信」，这不现实。

---

## 二、新入口：同形状事件走完整链路

RPC `notify_test` 的 `channel` 现在接受 `sms` / `call`：

```json
{"id":1,"method":"notify_test","params":{"channel":"sms","auth_key":"..."}}
```

后端构造一条与真实事件**同形状**的 `Notification` 交给 `notify()`，于是走的是完全相同的路径：

```
总开关 notify_enabled → 分类开关 notify_sms / notify_call
  → 短信/来电实时直发 send_realtime()（不等 notify_interval 合并窗口）
  → 文案模板 notify_tpl_sms / notify_tpl_call 渲染
  → 通道投递（企业微信 webhook / QQ 机器人）
```

因此收到的文本与真实短信/来电**一字不差**。模拟环境实测（`tests/mock-modem/simulate-push.js`）：

```
--- 短信测试 ---
喵呜～，有新短信到啦！快来看看是谁给你发消息了喵~
发送者: 138****0000
内容: 这是一条模拟短信，用于验证推送通道与文案模板（测试消息，非真实短信）

--- 来电测试 ---
喵呜～有电话打进来啦，快接起来看看是谁找你喵！
时间：2026-10-11 17:51:45
号码：138****0000
状态：来电振铃（测试消息，非真实来电）
```

两条推送分别在 **104 ms / 107 ms** 内送达 webhook，与真实短信/来电一样不等 60 秒合并窗口。

反过来对照：真实事件（由 mock 模组用 `AT+TESTPUSH` 模拟 URC）走的是同一条路，输出形态完全一致 —— 这正是「同形状」的验证点。

## 三、测试消息必须一眼认得出是假的

测试推送是给用户**自己**看的，若不加区分就可能被当成真事：

- **号码用掩码** `138****0000`，刻意不用 `13800138000` 这类看起来像真号的号码 —— 用户可能真的回拨过去；
- **正文自带标注**「（测试消息，非真实短信 / 非真实来电）」；
- 发送者字段仍是 `来电提醒`（与真实来电一致），保证 `{sender}` 占位符的行为不变。

---

## 四、开关没开时必须报错，而不是假装成功

这是本方法最关键的契约。

`Notifier::notify()` 在总开关或分类开关关闭时是**静默 return** 的（这是原设计：关的是「推送」，不是「记录」）。若照直调用后返回 `Ok`，界面会显示「发送成功」而手机毫无动静 —— **发送侧全绿、接收侧全无**，是最难排查的一类失败。

所以四种「发不出去」各自带可辨文案，并逐条加单测锁定：

| 情形 | 返回的错误 |
|:--|:--|
| 总开关关闭 | `自动推送总开关已关闭，事件不会推送（当前只记本地日志）` |
| 该类型开关关闭 | `「新短信」的事件推送开关已关闭` |
| 没有可用通道 | `没有已启用的推送通道（企业微信 WebHook 或 QQ 机器人）` |
| 类型不受支持 | `「信号变化」不支持测试推送（只有短信与来电需要按类型验证，其余走合并窗口）` |

LuCI 前端会把后端给的原因**原样转述**在按钮下方，不再只显示「失败」。

## 五、信号不提供类型化测试

信号指标是**真实读数**：`AT^HFREQINFO?` 给频点与带宽、`AT^MONSC` 给 RSRP/RSRQ/SINR，再由 `signalwatch` 渲染成九行评估。

造一条假的「RSRP -xx dBm」只会误导 —— 用户看到「信号极佳」却上不了网时，会先去怀疑网络而不是先怀疑这条测试消息。因此：

- `channel=signal` / `channel=memory_full` 不做注入，返回**说明理由**的错误；
- 信号要验证，用真实巡检：把 `notify_poll_interval` 临时调小（下限 30 秒）等一轮即可，或直接看通知日志 `/tmp/at-notifications.log` 里的历史巡检记录。

## 六、存储满提醒换成喵系口吻

原文案：

```
⚠️ 警告：短信存储空间已满
请及时处理，否则可能无法接收新短信
```

新文案：

```
喵呜～短信存储空间已经满啦，请尽快清理一下喵，不然可能收不到新的短信了哦！
```

改的不只是语气。存储满与其它三类事件有个本质区别：**它是用户自己就能解决的事** —— 删几条短信即可恢复。用「⚠️ 警告」这种系统告警口吻，会让人以为设备出了故障；改成提醒口吻，并把后果（收不到新短信）讲清楚，用户才知道该做什么。

与短信/来电一样，**已自定义过文案的设备不受影响**：后端只在 `notify_tpl_memory` 为空时回落默认值。

## 七、批量汇总标题换成喵系口吻

```
📑 批量通知汇总        →    喵～有一批新通知需要查看哦，快来看看都有哪些消息吧！
```

原标题只说明了「这是一批」，没有告诉用户要做什么；新标题把动作（查看）和范围（一批）都讲清楚，语气与短信/来电/存储满一致。

**顺带修了一条会随文案失效的断言**：`simulate-push.js` 的「未走批量汇总形态」原来是拿旧标题原文当判据 ——

```js
check('未走批量汇总形态', smsRec.content.indexOf('批量通知汇总') < 0);
```

这类断言的危险在于：文案一换它就**永久通过**，无论实现是否真的走了汇总形态，看报告永远是绿的。改为按新标题判定。

- **端到端 15 条**：RPC 成功、送达 webhook、不等合并窗口、模板占位符被真实填上、自带测试标注、不含插件名、非法 channel（`no-such-channel`）明确报错、`signal` 给出「不支持」的理由。

## 九、安全约束：IMEI 与恢复出厂设置不可触碰

本轮全程遵守该硬约束。类型化测试推送**不下发任何 AT 命令** —— 事件在进程内构造，纯本地链路，连只读查询都没有。三层护栏照旧生效：

```
扫描下发命令 35 条，其中危险命令 0 条，被拒 3 次（均为护栏自检）
```

## 升级方式

```sh
# apk 系统（OpenWrt 25.x / ImmortalWrt SNAPSHOT）
apk add --allow-untrusted ./<ARCH>-luci-app-mt5700-1.14.19-r1.apk

# opkg 系统（OpenWrt 24.10 及更早）
opkg install ./<ARCH>-luci-app-mt5700_1.14.19_<ARCH>.ipk
```

升级后建议重启服务并清理 LuCI 前端缓存：

```sh
/etc/init.d/at-webserver restart
rm -rf /tmp/luci-modulecache /tmp/luci-indexcache
```

> 本版改动了前端 JS（通知卡片新增两个按钮）与后端 RPC，**必须清 LuCI 缓存**，否则页面仍会执行旧脚本。
