# v1.14.21

**主题**：修正 v1.14.20 中旧键 `notify_interval` 的迁移策略 —— **出厂默认值不参与换算**。

这是一个小版本，只改迁移这一件事。若你尚未安装 v1.14.20，直接装本版即可；若已装 v1.14.20 且发现推送变成每分钟一条，升级到本版就会恢复为 10 分钟一次。

## 问题

v1.14.20 把 `notify_interval`（秒）统一按「向上取整到分钟」迁移。但 **60 秒是出厂默认值** —— 包内 `root/etc/config/at-webserver` 原本就写死 `option notify_interval '60'`，所以实机上看到这个值，绝大多数代表「用户从没改过」，而不是「用户刻意选了 60 秒」。

后果：升级后每台设备都变成**每分钟推一条**，即每天 1440 条，远超 QQ 官方主动消息频控（单关系 20 条/分钟、群 30~60 条/分钟、1000 条/群/天）。一次语义升级变成了推送轰炸。

## 修正后的规则

| 旧值 | 含义 | 迁移结果 |
|:--|:--|:--|
| `60`（秒） | **出厂默认值**，代表「从没改过」 | 新默认值 **10 分钟** |
| 其它值（如 `300`） | 用户真的改过 | 向上取整换算（300 秒 → 5 分钟） |
| `30`（秒） | 用户真的改过 | 1 分钟（最短间隔） |

前端加载时的换算显示与后端同口径 —— 否则界面算出 1 分钟、后端实际跑 10 分钟，用户会以为改了没生效。

## 为什么默认间隔是 10 分钟

定时推送**每到一个间隔必定发一条**（与期间有没有事件无关）。若沿用旧默认的 60 秒，就是每天 1440 条；10 分钟为每天 144 条，是「状态新鲜」与「不刷屏」之间的平衡点。想要更实时，把 `notify_timer_interval` 调小即可（最小 1 分钟），但请先评估 QQ 频控。

## 升级

```sh
apk add --allow-untrusted ./<ARCH>-luci-app-mt5700-1.14.21-r1.apk
# 或
opkg install ./<ARCH>-luci-app-mt5700_1.14.21_<ARCH>.ipk
```

升级后确认实际生效的间隔：

```sh
uci show at-webserver.config | grep notify_timer_interval
# 期望：notify_timer_interval='10'（由出厂默认值 60 秒迁移而来）

# 或看启动日志
logread | grep '定时推送已启动'
# 期望：定时推送已启动：每 10 分钟推送一次当前实际情况（信号读数 + 存储状态）
```

## 验证

- `cargo test` **141 passed / 0 failed / 2 ignored** —— 新增 `legacy_default_seconds_falls_to_new_default_not_one_minute`，钉住 60 秒 → 10 分钟、300 秒 → 5 分钟、30 秒 → 1 分钟；
- `simulate-push.js` **62 通过 / 0 失败** —— 端到端改用**非默认值 30 秒**验证换算路径（60 秒走的是新默认值分支，换算不出可观测的短间隔），实测收到「🕒 当前状态（定时推送）」状态快照；
- 本轮不触碰 IMEI 与恢复出厂设置。
