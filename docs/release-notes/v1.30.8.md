# v1.30.8 发布说明 — 冗余代码清理（死代码删除 / 生命周期收敛 / 重复逻辑合并）

本次不改功能，是一次结构性清理。净减约 430 行，涉及 19 个文件。清理过程中另发现并修掉两个缺陷：切页钩子的快照时序、NR-ARFCN 频段表的区间错误。

## 问题

三处冗余各自造成实际后果，不只是「代码不好看」：

1. **「离开页面」的清理从来没有执行过。** 7 个视图各写了一套 `_dispose`，但 LuCI 的 view 生命周期里**根本没有 `_dispose` 这个钩子**，它从未被调用过。后果是切页后推送订阅不退订、会话租约不释放、挂在 `document` / `window` 上的监听器不摘除 —— 越切越多的僵尸订阅堆在后台。

2. **同一份逻辑散落在多处，各自演化出不同口径。** ARFCN → 频段的映射存在三份实现，其中 `network_settings` 那份把 n77 排在 n78 之前，导致 n78 分支**实际不可达**；`sms_center` 与 `network_status` 各有一套字节格式化，KB 位一个 1 位小数、一个 2 位，且 `sms_center` 那套完全没有 GB 层级。

3. **单文件内的复制粘贴块。** `logs.js` 的「下拉美化」出现三次、滚动按钮两次、过滤器两次；`service.js` 的 procd 实例扫描三次；`sms_center.js` 的弹窗脚手架四处。每次改样式或加校验都要改三四遍，漏改一处就出现行为分叉。

## 根因

- `_dispose` 属于「看起来该有的钩子」——名字符合直觉，LuCI 的文档与社区示例里也常见，但本仓库用的这套 view 扩展点并不支持它。写了不报错，因此长期未被发现。
- 重复实现不是一次复制出来的，是逐步长出来的：新页面要用到某段逻辑时从旧页面拷一份，之后各自按需求微调，最终同源不同义。这也是为什么三份频段表会有三种口径。
- 死代码则是几轮重构的残留：调用方改走新通道后，旧通道的函数留了下来，且没有任何机制标记它们已无人调用。

## 顺带修掉的两个缺陷

### `ui.js`：切页钩子的快照时序

`_installHashHook` 原先这样写：

```js
window.addEventListener('hashchange', function () {
    // 延后一拍，避免同 tick 内先注册又被立刻清掉
    setTimeout(function () {
        var old = _hooks;   // ← 快照在 macrotask 里才取
        _hooks = [];
        old.forEach(function (fn) { fn(); });
    }, 0);
});
```

问题在于**快照本身也被推迟了**。`setTimeout(0)` 排的是宏任务，而 LuCI 的路由派发在当前宏任务结束后、通过微任务完成视图的 load/render。若某个视图的 `load()` 能纯微任务走完（无网络边界，例如命中本地缓存），它会在 `setTimeout(0)` 回调**之前**渲染完毕并注册钩子 —— 新页的钩子被 `old` 捕获并立刻执行。

后果是刚进页面就被摘掉自己的轮询与监听器，最坏情况误调 `sms_center` 的 `closeSession()`，正好是本 PR 想解决的「租约长期续命」的反面。「延后一拍」只把竞态窗口挪了个位置，没有消除它。

改为**同步快照、延后执行**：

```js
window.addEventListener('hashchange', function () {
    var leaving = _hooks;   // 本 tick 内取：此刻目标视图尚未渲染
    _hooks = [];            // _hooks 里只可能是离场视图的钩子
    setTimeout(function () {
        leaving.forEach(function (fn) { fn(); });
    }, 0);
});
```

执行仍延后一拍，保留「等路由派发完成再清理、避开与 LuCI DOM 更新的竞争」的原有意图。

需要说明的是：按当前 12 个视图的实现，`load()` 里都有 UCI / procd / RPC / AT 网络请求，走的是宏任务，日常切换**不会**触发该竞态。它属于「现在不痛、但 3 行就能修掉」的隐患 —— 一旦将来某个页面走纯缓存快速路径，或 `Ui.interval` 被挪到 `load()` 阶段，它就立刻变活。

### `parse.js`：按 TS 38.104 订正 NR-ARFCN 频段表

清理时把三份频段表合成一份，原实现为消除「n78 不可达」直接**删掉 n77、把 n78 拉宽到 680000**。这引入了一个新错误：n78 的标准区间是 620000–653333（3.3–3.8GHz），653334–680000（3.8–4.2GHz）是 **n77 独有**，拉宽后会被误标成 n78。

按 3GPP TS 38.104 Table 5.4.2.3-1 订正为调顺序而非改区间：

```js
var NR_ARFCN_BANDS = [
    [1, 422000, 434000], [3, 361000, 376000], [5, 173800, 178800], [8, 185000, 192000],
    [28, 151600, 160600], [41, 499200, 537999],
    [78, 620000, 653333], [77, 620000, 680000], [79, 693334, 733333]
];
```

n78 排在 n77 之前，重叠区（620000–653333）按国内现网部署约定判 n78，653334–680000 判 n77。顺带订正两处历史遗留区间：n3 应为 `361000–376000`（原 `376000–396000`）、n5 应为 `173800–178800`（原 `173800–175000`）。

## 取舍：两处会看到但无害的显示差异

清理不可避免地把口径统一到其中一份，两处因此产生可观测变化：

1. **字节格式化的 KB 小数位 1 → 2**。统一到 `rpc.js` 的 `formatFlow`（`toFixed(2)`）后，`25.9 KB` 显示为 `25.88 KB`。纯精度显示变化。另一方向是修正：≥1GB 由原来「没有 GB 层级」（`5120.0 MB`）变为正常显示 `5.00 GB`，≥1TB 同理。

2. **`service.js` 的 procd 状态判定兜底被统一抬齐**。合并后的 `scanProcdInstances` 采用了 load 路径的写法，带顶层 `svc.running` / `svc.pid` 兜底；而 `fetchRunning`、`refreshStatus` 原本不带。统一后三者口径一致，等于消掉了「首屏显示运行中、重载后复查找不到」这个既有不一致。标准 procd 应答顶层不含这两个字段，正常环境不触发；仅在非标准应答下可能偏乐观地标为「运行中」。

## 升级注意

视图现已依赖 `ui.js` 新增的 `Ui.onLeave` / `Ui.interval`。**升级时必须与 `ui.js` 同批部署** —— 若浏览器缓存了旧版 `ui.js`，render 会抛 `Ui.onLeave is not a function`，页面空白。手动替换文件升级时需强制刷新浏览器缓存。
