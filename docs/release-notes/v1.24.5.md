# v1.24.5

**主题**：修复短信中心「点发送显示成功、短信实际没发出去」（issue #19）。根因是 PDU 提交字符 Ctrl+Z 从未下发；纯前端协议修复，后端与 AT 通道零改动。

---

## 1. 要解决的问题

用户在短信中心给联系人发短信：点「发送」弹出**发送成功**，但对方**从未收到**，模组存储里也没有这条已发短信（接收短信一直正常）。

### 1.1 根因：两段式协议被写成一条命令，且丢了提交字符

3GPP TS 27.005 §3.4.1 规定 PDU 模式发短信是**两段式**交互：

1. 主机发 `AT+CMGS=<TPDU长度>` → 模组回 `> ` 输入提示符（注意：无换行结尾），进入 PDU 等待态；
2. 主机发 `<PDU hex>` + **Ctrl+Z（0x1A）** → 模组执行发送，回 `+CMGS: <mr>` + `OK`。

旧实现把两步拼成**一条**命令 `AT+CMGS=<长度>\r<PDU>` 交给后端，后端原样写入串口（仅末尾补 `\r`）。于是：

- 模组收到 `AT+CMGS=<长度>\r` 后只回 `> ` 提示符；
- 后端的 `consume()` 又把 `> ` 判定为「应答结束」（这段逻辑本是给终端页手工输入 PDU 用的），前端因此拿到 `success=true`；
- **而 0x1A 从未出现在串口上** —— 模组一直停在 PDU 输入等待态，短信根本没有发出去。

前端只检查 `success === false`，提示符应答又恰好是 success，于是「发送成功」照常弹出。mock 模组不模拟 `> ` 提示符（对 `AT+CMGS=<len>` 直接回 OK），所以既有测试完全看不到这条路径。

## 2. 实现

### 2.1 前端：拆成两条命令，补上 Ctrl+Z（`view/at-webserver/sms_center.js`）

- 第一步 `sendCommand('AT+CMGS=' + part.tpduLength)` 单独发，等模组的 `> ` 提示符应答；
- 第二步 `sendCommand(part.pdu + '\x1A')` 发 PDU + 提交字符，等 `+CMGS` 回执；
- 长短信分片时每片都走完整的「报长度 → 交 PDU」两步，片间仍串行；
- **任一步失败立即中断**发送链并报出模组的原始错误（旧代码只检查最后一条的应答，中间某片失败会被静默吞掉）；
- **假成功防护**：最终应答必须含 `+CMGS` 或 `OK`，否则判失败。只拿到 `> ` 这类提示符应答时不再显示「发送成功」——这正是 issue #19 的直接触发形态；
- 模式判断收紧：只有确认当前已是 PDU 模式（应答含 `+CMGF: 0`）才跳过切换，查询失败 / 应答无法解析时一律强制 `AT+CMGF=0`，杜绝「文本模式下 `AT+CMGS=<长度>` 被当成发给号码 <长度>」的歧义。

### 2.2 0x1A 过链路的可行性（逐段核实）

Ctrl+Z 要穿过四层才到串口，每一层都确认无损耗：

| 层 | 处理 | 结果 |
| --- | --- | --- |
| 浏览器 → rpcd | `JSON.stringify` 将 0x1A 转义为 `\u001a` | 解析还原 |
| rpcd → ucode 插件 | ubus blob → ucode 值，按字节传递 | 原样保留 |
| ucode → Rust | `mt5700.uc` 的 `sprintf('%J')`：`ucv_to_string_json_encoded` 对 <0x20 字符输出 `\u001a` | 转义合法 JSON |
| Rust → 串口 | `serde_json` 解析还原 0x1A，`write_all` 原样下发 | 字节到位 |

### 2.3 mock 模组：按真实协议复刻两段式（`tests/mock-modem/mock-modem.js`）

- `AT+CMGS=<len>` → 回 `\r\n> ` 提示符，**结尾不带换行**（后端正是靠「行尾残留全是空白与 `>`」识别提示符的，补了 `\r\n` 就测不到这条路径）；
- `<PDU>\x1A` → 回 `+CMGS: 1\r\nOK`；
- `AT+CMGS=0`（零长度 TPDU）→ `ERROR`；
- 旧拼法（长度与 PDU 同在一条命令里）不再被 mock 特殊照顾，按真实模组行为走提示符 + 拒答路径。

### 2.4 测试：发送流程第一次被真正覆盖（`tests/mock-modem/sms-center-render.js`）

原渲染测试的 `SmsEncode` 是个连 `buildSubmitParts` 都没有的 stub，`send()` 从未被测试跑到过——这正是 bug 溜过去的原因。现在：

- 加载**真实** `smsEncode.js`（vm 剥 LuCI 语法糖），PDU 用真编码器生成；
- 场景 A（正常两段式）：断言 `AT+CMGS=<长度>` 与 `<PDU>\x1A` 是两条独立命令、提交命令以 0x1A 结尾且去掉后是纯十六进制、**任何命令里都不允许出现 `\r` 拼 PDU**、成功后气泡/缓存/清空输入框齐全；
- 场景 B（假成功防护）：提交只回 `> ` 时必须报错、不得写缓存——复现 issue #19 的应答形态；
- 场景 C（文本模式）：必须先 `AT+CMGF=0` 再发；
- 场景 D（模组拒绝，如 `+CMS ERROR: 322`）：报错且不写缓存；
- **反向验证**：换回旧版前端跑新测试，17 条新断言中 8 条如期失败（含「没有任何命令把 PDU 用 `\r` 拼进 CMGS」「只有提示符应答时不得显示发送成功」），证明测试真能抓住这个 bug。

### 2.5 e2e：沿全链路钉住协议（`tests/mock-modem/e2e-test.js`）

新增「5b. 短信发送两段式协议」：`AT+CMGS=20` 须拿到提示符应答、`PDU + \u001a` 须拿到 `+CMGS` 回执（同时验证 0x1A 经 JSON 转义穿过 RPC 链路）、`AT+CMGS=0` 须被拒、旧拼法不得拿到提交回执。
