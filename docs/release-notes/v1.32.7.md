**性能与后端收口版** —— 状态页把「一轮 25 次 AT 查询」压成 1 次批量 RPC 并给静态项加 TTL 缓存；后端把采样、串口枚举、通知落盘等阻塞段收进 blocking 池，并把「下次别改回去」写成仓库强制规则。

### 为什么改

- 状态页每次刷新都要重新问模组一遍：既有「一轮内根本不会变」的型号、固件、IMSI/ICCID、APN 上下文、运营商名称，也有 25 次各自独立的 RPC 往返。实机测得分段结论（192.168.88.1，v1.32.6，普通模式冷启动）：一轮 25 条 AT 命令跨时 2141ms，其中静态项 10 条合计 856ms（66%）；单次 `mt5700.at` 调用里 17ms 属于 ucode 桥（写临时文件 + fork `nc` + rpcd 往返），25 次就白付 425ms；各任务之间的 Promise 串行空档另有约 400ms。
- 后端是 Tokio 多线程运行时，但采样、串口枚举、通知落盘等路径仍在 async 上下文里直接 fork `uci`、读写文件。实机测得单次 `uci show` 约 2.7ms，流量采样每秒要跑两次（合计约 5.4ms/秒），这段 CPU + fork 全部压在 reactor 线程上；通知日志若被配到闪存，一次 `append_capped`（metadata + 读改写）可到几十毫秒。

### 主要改动

- **perf(status) 静态项 TTL 缓存**：型号/固件/IMSI/ICCID 60s，SIM 状态、APN 上下文、运营商名称 15s，命中即跳过下发；`AT^EONS=2` 原本每轮重发，并入 TTL 后自然去重（只影响运营商文案，语义不变）。`AT+CGSN`（IMEI）不进缓存。
- **perf(status) 一轮合并为一次批量 RPC**：ucode 插件新增 `batch` 方法（一次写 N 行、一个 `nc`、读 N 行，单项返回契约与 `at` 完全一致，32 条上限、整批 18s 硬超时），前端 `ATClient.sendBatch` + 视图本轮预取；依赖本轮解析值的 `AT^DSAMBR=<cid>` / `AT^C5GQOSRDP=<cid>` 仍逐条下发，批量整体失败时全部退回逐条，行为与改动前一致。
- **perf(status) 不再下发必然失败的命令**：纯 NR SA 下 `AT^TRANSMODE?` 固定回 ERROR 却要占 64~173ms，本轮直接跳过，`state.mcs.tm` 同样置空，显示一致；LTE / EN-DC 行为不变（EN-DC 状态未知时照常查询，这是评审后补的修正）。
- **fix(acl)** read 侧 ACL 补 `batch` 方法名（rpcd 按方法名校验，缺项会被拒）。
- **perf(ui) 背景角色图按断点按需加载**：桌面与手机两张立绘原本都会下载，其中一张被 `display:none` 隐藏；现在只为当前断点可见的那张下发 `src`，跨断点再按需补图。实机（冷缓存，同页两次对照）：状态页 1.526→1.424 MB、短信页 1.494→1.402 MB、日志页 1.722→1.631 MB（-4.9%~-6.7%），首屏可交互 853→710 / 910→649 / 813→721 ms。极简模式本就不挂载背景层，逻辑保持原样。
- **refactor(backend) 阻塞调用收口**：`usage.rs` 的 `read_counters_netdev`（两次 `uci show` + sysfs 读取）整段搬进 `spawn_blocking`；`localtime::init`、`Notifier::new`、`UsageTracker::new`、`QqSender::from_config`、`serialdetect::list_serial_candidates` 与通知日志写入同样收口到 blocking 池，启动顺序不变。
- **refactor(backend) 冗余清理**：删除 `atclient` 里与 `schedule::sleep_ctx` 完全相同的私有副本（6 行），`ringlog` 的分类过滤改用 `contains`，删除 `tabmenu.js` 中零调用的 `findTabContainer()`。
- **docs(agents) Rust/Tokio 健康规则**：`AGENTS.md` 新增「五、Rust/Tokio 后端健康规则」，把本版的口径固化成强制条款 —— `cargo test` 全绿、生产段零告警、async 路径禁阻塞（无法异步化走 `spawn_blocking`）、跨 `await` 用 `tokio::sync::Mutex`、`at_queue` 单通道串行不得破坏、`shutdown_signal()` 与 5 秒收尾路径不得回归、新增 `tokio::spawn` 须能回答「谁取消 / 谁 await / 失败是否被吞」。
- **note(backend) 不改 ucode 桥**：实测单次 RPC 往返约 5ms（`ubus call` 口径含客户端 fork），25 次合计约 125ms、占一轮 2141ms 的 5.8%；批量合批已在 PR #51 落地，再改同一段会产生硬冲突，故只在文档记录数据。

### 验证记录

- 合并后 main 本地实测：`cargo test` **356 passed / 0 failed / 2 ignored**；`node tests/static-check.js` **4/4**；22 个 `tests/*-test.js` 全部通过。
- 状态页性能（实机 192.168.88.1，同一无头浏览器、同一采集脚本，冷/热各一轮）：首轮普通/精简 2141→1619ms、2325→1762ms（-21%~-25%）；稳态轮（第 2 轮起）1959→362ms、2030→571ms（-72%~-82%）；一轮里含 AT 的 RPC 次数 25~26→1~5。两模式首屏文本行数、面板坐标、关键字段（运营商、IP、PCI、TAC、网络制式）与改动前逐项一致，无 404、无 console error。
- 未验证项：Rust 二进制此前没有设备侧部署实测（需要交叉编译，本地未跑长时间构建），本版随云编译产物一起装机，装机后进程与日志是本版第一次实机验证；未做长时间运行下的缓存击穿 / 批量超时压力验证；前端改动只在 1280×900 视口下做过两模式对照。
- 改动文件 CRLF 计数为 0，UTF-8 无 BOM。

### 升级提示

- 覆盖安装即可，无配置迁移。`MT5700_UI_VERSION` 1.32.6 → 1.32.7，浏览器模块缓存整体失效；`MT5700_CSS_VERSION` 保持 2.46.9（本版未改样式文件，不额外触发样式重取）。
- 状态页首次进入仍要等一轮完整查询（冷缓存没有 TTL 命中），从第二轮回起才体现节流收益。
- 批量失败会整体退回逐条，行为与升级前一致，不会出现空白页；想确认批量是否生效，看浏览器网络面板里 `mt5700.batch` 的调用。
