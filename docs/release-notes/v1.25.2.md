# v1.25.2

**主题**：修复「短信显示发送成功、实际发不出去」的**真正成因**。v1.24.5 的方向是对的（缺提交字符），但那个提交字符从来没到过模组——它在传输链路里被改写成了普通文字的六个字符。

---

## 1. v1.24.5 修了，但 issue #19 还在

issue #19 的反馈者升级到 v1.24.5 后，界面从「假成功」变成明确的失败：

```
↑ 发送
<PDU>u001a
AT 命令失败: ... -> 模组无响应（已等待 2000ms）
```

三个细节值得注意：

1. 命令里能看到 `u001a` —— 不是 `^\Z` 之类的控制字符显示，而是**六个可见字母**；
2. 模组没有回 `+CMGS`，也没有回 `+CMS ERROR`，是彻底沉默；
3. 失败原因是 2 秒超时，不是「模组拒绝」。

## 2. 取证：0x1A 在链路里被吃掉了

用后端自己的内存日志（`ubus call mt5700 logs`）把"写进串口的原文"打出来做十六进制核对。
把日志按 `发送 → 模组: ` 之后的命令文本取出来，对尾部六字节做 `hexdump -C`，
看到的形状是：

```
$ ubus call mt5700 logs '{"since":0,"limit":1200}' | grep '发送 → 模组: AT+CMGS' | ...
...  43 75 30 30 31 61   |Cu001a|
```

`43 75 30 30 31 61` = `C` `u` `0` `0` `1` `a`。如果真的是 0x1A 控制字节，JSON 里会被转义成 `\u001a`（`5c 75 30 30 31 61`，**多一个反斜杠**）。这里没有 0x1A、也没有反斜杠 —— 也就是说，**写进串口的是字面量 `u001a` 这六个字符**。

> 这里只保留结论所需的六个字节；当时的完整 dump 里还带着报文原文与设备上的日志上下文，
> 已按脱敏要求删除。

模组收到一串十六进制字符之后跟了 6 个字母，它当然不会认为这是提交，于是继续等；我们等 2 秒判超时。这就是 issue #19 的完整链路。

链路本身是四层：

```
浏览器 JSON.stringify → rpcd → ucode(sprintf %J) → nc → Rust serde_json → 串口
```

单独验证过 ucode 的 `%J` 是**正确的**：

```
$ ucode -e 'print(sprintf("%J", {cmd: "A"+chr(26)+"B"}),"\n")' | hexdump -C
00000000  7b 20 22 63 6d 64 22 3a  20 22 41 5c 75 30 30 31  |{ "cmd": "A\u001|
00000010  61 42 22 20 7d 0a                                 |aB" }.|
```

反斜杠在。所以问题出在这条链路的其它环节（rpcd 的 JSON 解析 / ubus blob 传递），具体哪一跳丢的不重要 —— **结论是：任何需要精确控制字节的命令，都不该走这条链**。

## 3. 修法：改成单次写入，根本不需要控制字符

手册 9.14.5 的示例本来就是一种写法：

```
输入： AT+CMGS=18\r0015660B3108108300F00008FF044F60597D
输出： 0015660B3108108300F00008FF044F60597D--[message]->
       +CMGS: 135
       OK
```

也就是说：**长度与 PDU 放在同一条命令里，用 `\r` 分隔**，提交不需要 Ctrl+Z。

顺手解包上游 `at-webserver` 3.0.2 的 ipk 做交叉验证，其前端 bundle 里就是这一句：

```js
await ls().sendCommand(`AT+CMGS=${vt[mt].tpduLength}\r${vt[mt].pdu}`)
```

两端（手册示例 + 上游实现）一致，说明这就是这颗模组实际接受的写法。于是把前端从"两段式"改成单次写入：

```js
AtWs.client.sendCommand('AT+CMGS=' + part.tpduLength + '\r' + part.pdu, SMS_SUBMIT_TIMEOUT_MS)
```

整条命令只有 ASCII 可见字符，**不含任何控制字符**，天然免疫上面那类转义破坏。尾部的 `\r` 由后端统一补（原有逻辑：命令末尾没有 CR 就补一个）。

## 4. 第二个坑：2 秒超时本来就不够

改完写法，还有一层：后端对所有用户命令统一用 `COMMAND_TIMEOUT = 2s`。普通查询是模组本地算完就回，2 秒够；但短信提交要把 TPDU 交给网络侧，`+CMGS` 的回执取决于信号与基站排队。本机实测 RSRP 只有 **−107 dBm**（弱信号），2 秒必然超时。

「超时」在这里比「失败」更糟：短信可能已经发出去了，界面却报失败，用户重发就会重复计费。

因此给提交单独一套预算，三层配套：

| 层 | 常量 | 值 | 作用 |
| --- | --- | --- | --- |
| Rust | `SMS_SUBMIT_TIMEOUT` | 40s | 等模组回执 |
| ucode | `SMS_RPC_TIMEOUT_SEC` | 50s | nc 硬超时，比后端大 10s，保证先拿到后端结论 |
| 前端 | `SMS_SUBMIT_TIMEOUT_MS` | 45s | 单次覆盖，默认仍是 14s |

识别方式统一为「命令以 `AT+CMGS=` 开头**且含 CR**」——只报长度的那半步（`AT+CMGS=14`，不含 CR）仍走原来的短超时。其余所有命令的超时**一个字都没改**，避免后端真挂掉时整页的失败反馈变迟钝。

## 5. 验证

- **Rust**：`cargo check` 通过（本次改了 `atclient.rs` / `rpcserver.rs`）；
- **ucode**：改后在实机 `loadfile` 语法校验通过；
- **手册核对**：`<length>` 语义为「TPDU 字符个数除以 2」（§9.12.3 明确写了），即不含 SMSC 的字节数 —— 我们传的 `tpduLength` 与此一致；
- **控制字节取证**：后端日志 hexdump 确认串口收到的是字面量 `u001a`（六个字节 `43 75 30 30 31 61`，见 §2）；
- **写入口径对照**：手册 9.14.5 示例与上游 3.0.2 bundle 双向印证（见 §3）。

## 6. 升级注意

- 短信发送路径改动涉及前端、ucode、Rust 三处，**必须整包升级**，单独替换前端文件不会生效（超时在 Rust 与 ucode 侧）。
- 提交最长可能等 40 秒才给结论（弱信号）。界面上按钮在此期间置灰，属正常现象 —— 比"秒回失败、实际已发出"要安全。
- 之前若因反复发送产生重复短信，本版本不会重发历史内容，仅是修正提交方式。
