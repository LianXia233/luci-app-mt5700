# v1.14.16 发布说明

**v1.14.16 为通知链路时效性与自动化版本**：新增自动推送总开关、把短信与来电改为实时直发、并新增「信号定时巡检」以修复「信号变化通知开关在实机无效」的缺陷。**未触碰任何 IMEI 相关代码与数据流**。

---

## 一、信号定时巡检（本轮核心修复）

### 症状

LuCI 通知卡片里的「信号变化通知」开关打开后，无论信号怎么变化都收不到任何推送。

### 根因

本模组（TDTECH / Fibocom 系）**不会主动上报** `^HCSQ` / `^CERSSI` 这两条信号读数：

- 实机抓取的 **1200 条 AT 记录里，自发信号上报为 0 条**；
- 前端页面轮询也从不发这两条查询（它只走 `AT^MONSC` 一类状态查询）；
- 于是 `urc::Dispatcher::handle_signal()` **从未被调用过** —— 该开关在实机是死的，与配置、通道、凭据都无关。

### 修复

新增 `signalwatch` 模块：后端在**用户指定的时段内**按间隔主动查询信号，让开关真正生效。

| 配置项 | 作用 | 默认值 | 取值范围 |
|:--|:--|:--|:--|
| `notify_poll_enabled` | 是否启用信号定时巡检 | `1` | `0` / `1` |
| `notify_poll_start` | 时段起点 `HH:MM` | `00:00` | `00:00`~`23:59` |
| `notify_poll_end` | 时段终点 `HH:MM` | `23:59` | `00:00`~`23:59` |
| `notify_poll_interval` | 巡检间隔（秒） | `300` | `30`~`3600` |
| `notify_poll_all` | `1`=每次巡检都推送状态 | `0` | `0` / `1` |
| `notify_poll_delta` | 变化阈值（dB，仅 `notify_poll_all=0` 时生效） | `3` | `1`~`30` |

**时段外一条 AT 都不发**：既不占用串口，也不会在半夜无意义地打扰用户。

时段语义的三种形态（`in_poll_window`）：

- 普通区间：`08:00` → `18:00`；
- **跨零点**：`22:00` → `06:00`（起点晚于终点即视为跨零点）；
- 起止相同（如 `00:00` / `00:00`）：视为**全天** —— 否则按区间解释只会命中一分钟，用户会以为功能坏了；
- 格式非法：回落全天并在启动日志记一条告警，避免因笔误彻底静默。

区间取**闭区间**（两端都算在时段内）。这一条是测试逼出来的修正：默认全天 `00:00-23:59` 若用半开区间，会漏掉当天最后一分钟（23:59）—— 单测直接把这个问题暴露了出来。

### 推送策略：「仅变化时推送」的基线只在推送时刷新

若每次读数都刷新基线，信号从 -80 缓慢漂移到 -95（每次仅差 2 dB）将**永远越不过阈值**，用户反而收不到「信号持续变差」这个最该知道的通知。因此基线以「上次通知时的值」为准。

另外两条兜底策略：

- **首次读数恒定推送一次** —— 让用户立刻确认「这个功能真的在工作」，否则默认策略可能几小时不出声，看起来像坏的；
- **制式切换（LTE ↔ NR）必定推送** —— 即便 RSRP 数值恰好没变，这也是用户最关心的网络事件之一。

### 睡眠切片

轮询间隔最长可达 1 小时。若一次睡满，用户把时段起点设成「10 分钟后」时要等满一个间隔才会开始工作。因此睡眠切成 **≤30 秒**的片段：时段边界最多迟到 30 秒生效，而片段期间不做任何 AT 操作，代价可忽略。

### 读数口径统一

抽出纯函数 `parse_signal_reading()`，URC 分发与定时巡检**共用同一套换算规则**：

- `^HCSQ:` —— LTE 为 `<rssi>,<rsrp>,<sinr>,<rsrq>`，故 RSRP 取下标 2；其余制式取下标 1；`255` 表示「未知或不可测」，视为无有效读数；换算 `RSRP = raw - 140`；
- `^CERSSI:` —— 第 19 个字段（下标 18）已是 dBm，不再做换算。

若两条路径各写一份，同一信号会出现两个不同的 dBm 值。

## 二、自动推送总开关

新增 UCI `notify_enabled`（默认 `1`），由用户在 LuCI 上一键启停全部推送。

**关闭后的行为**：

- **不再外发任何消息**（企业微信 / QQ 均静默）；
- **仍然写本地通知日志** —— 关的是「推送」而不是「记录」，留着事后追溯；
- **停止信号定时巡检** —— 关掉自动推送后若后台还在周期性占串口，用户会以为开关无效。

`Notifier::notify()` 的判定顺序为：**总开关 → 事件类型开关 → 通道可用性**。`flush_all()` 同样在总开关关闭时丢弃待发队列并留痕：事件可能在入队之后才被关掉，此时保留队列已无意义。

### LuCI 联动置灰

通知卡片最前新增「自动推送总开关」，关闭时联动置灰四个事件类型开关与整块巡检子区块（启用开关 / 时段 / 间隔 / 策略 / 阈值）。置灰后控件不再响应输入，用户一眼能看出哪些项当前不起作用。

## 三、短信 / 来电实时推送

短信与来电改走**实时直发**路径（`send_realtime()`），不再进入合并窗口 —— 这两类是「错过了就没意义」的事件。

| 事件 | 来源 | 推送路径 |
|:--|:--|:--|
| 新短信 | 模组主动上报 `+CMTI:` | **实时直发** |
| 来电 | 模组主动上报 `RING` | **实时直发** |
| 存储满 | 模组主动上报 `^SMMEMFULL` | 合并窗口 |
| 信号 | 后端定时巡检 | 合并窗口 |

信号与存储满保持合并窗口，避免把 QQ 主动消息频控（单关系 20 条/分钟）打满。

**边界处理**：通道尚未就绪（bind 模式未绑定）时，实时事件仍会入队而不是直接丢弃，绑定成功后由 `flush_all` 补发，保持 v1.14.15 建立的「绑定前后事件零丢失」语义。
