# v1.14.18

> 上一版：v1.14.17（时间口径统一系统时区 + 巡检完整信号评估 + 短信中心收发分区）
> 本版聚焦三件事：**巡检推送显示具体频段与网络代际**、**推送文案压缩精简**、**短信中心会话改为聊天式单时间轴**；顺带修掉「存储用量恒为 0 / 0」这个真实缺陷。

## 一、巡检推送：显示具体频段与网络代际

### 现象

推送里只写得出「中频 2565 MHz」这类描述。2565 MHz 这个数字对判断链路质量帮助有限 —— 用户真正想知道的是「现在跑在哪个频段上」（n41 还是 n78，B3 还是 B8）。

### 根因

`AT^HFREQINFO?` 的应答是：

```
^HFREQINFO: <n>,<sysmode>,<band_classN>,<dl_fcnN>,<dl_freqN>,<dl_bwN>,<ul_fcnN>,<ul_freqN>,<ul_bwN>
```

上一版只取了索引 `[4]`（下行频点）与 `[5]`（下行带宽），**索引 `[2]` 的频段号被整段丢弃**。字段就在应答里，白白浪费。

### 修复

- 新增 `HfreqCarrier` 结构承载 `<sysmode>` / `<band>` / 下行频点 / 下行带宽；
- 频段解析抽成纯函数 `parse_hfreq_line()` —— 「字段取错下标」这类缺陷只有对着**实机原始应答**才看得出来，抽成纯函数才写得成回归用例；
- 频点 ≤ 0 视为「没有读数」而非「0 Hz」：未注册 / 无服务时模组会把频点填 0。

### 前缀不靠猜

| 制式 | 写法 | 示例 |
|:--|:--|:--|
| NR | `n` 前缀 | `n41` |
| LTE | `B` 前缀 | `B3` |
| 制式未知 | 中性的 `Band` | `Band 41` |

第三行是有意为之：**频段号拿到了、代际却不知道时，不猜它是 4G 还是 5G**，退成中性的 `Band 41`。

### 一个不显眼但会埋雷的坑

`^HFREQINFO` 的 `<sysmode>` 编码与 `^SYSINFOEX` 的 `<sysmode>` **不是同一张表**：

| 命令 | 编码表 |
|:--|:--|
| `^HFREQINFO` | `1` GSM / `3` WCDMA / `6` LTE / **`7` NR** |
| `^SYSINFOEX` | `6` LTE / **`11` NR-5GC** |

两者混用会把 NR 误判成 LTE（`7` 在 `^SYSINFOEX` 表里根本不是 NR）。代码里为此单列了 `hfreq_sysmode_name()` 并配了断言 `hfreq_sysmode_codes_differ_from_sysinfoex`。

### 制式来源的兜底顺序

制式优先信 `^MONSC`；当它没给出制式时，用 `^HFREQINFO` 的 `<sysmode>` 兜底 —— 否则会出现「拿到了频段号，却不知道该写成 `n41` 还是 `B41`」的尴尬。

### 实机证据

原始应答（MT5700M-CN，实机）：

```
AT^HFREQINFO?
^HFREQINFO: 0,7,41,513000,2565000,100000,513000,2565000,100000
```

实际推送正文：

```
📶 5G 信号巡检
时间：2026-10-12 00:58:17
频段：n41 · 2565 MHz / 100 MHz（接近 5G 单载波满配）
网络能力：优秀 —— 信号与频段带宽俱佳，适合高清视频及大文件下载

RSRP -62 dBm（≥ -80）  极佳 · 覆盖极佳
RSRQ -10 dB（≥ -10）  极佳 · 纯净通畅
SINR 29 dB（≥ 20）  极佳 · 顶速阶数
SIGNAL 100%（满分）  极佳 · 满格服务
```

## 二、推送文案压缩（12 行 → 9 行）

信息量增加的同时反而更短：

| 变化 | 说明 |
|:--|:--|
| **代际进标题** | `📶 5G 信号巡检` / `📶 4G 信号巡检`，一眼看出当前是几代网络 |
| **新增频段行** | `n41 · 2565 MHz / 100 MHz`；缺哪项就少哪项，不写占位符 |
| **总评一行** | `网络能力：优秀 —— <场景说明>` |
| **四指标各一行** | 原来的「基准 → 实测 → 结论」三段式压成 `RSRP -62 dBm（≥ -80）  极佳 · 覆盖极佳` |

与网页「射频信号质量」卡片的口径仍**逐项一致** —— 分级规则由 `signalgrade` 模块单点维护，网页与推送共用，不会出现「同一组读数两个结论」。

## 三、推送文案：短信与来电换成喵系口吻

短信与来电提醒的首行文案换成更口语化的写法 —— 这两类是日常频率最高的通知：

| 事件 | 新首行 |
|:--|:--|
| 短信 | `喵呜～，有新短信到啦！快来看看是谁给你发消息了喵~` |
| 来电 | `喵呜～有电话打进来啦，快接起来看看是谁找你喵！` |

`{sender}` / `{content}` 等占位符与后续行保持不变。实际推送形如：

```
喵呜～，有新短信到啦！快来看看是谁给你发消息了喵~
发送者: 13800138000
内容: 明天上午的评审改到十点，方便吗？
```

```
喵呜～有电话打进来啦，快接起来看看是谁找你喵！
时间：2026-10-12 01:28:29
号码：13800138000
状态：来电振铃
```

### 已经自定义过文案的设备不受影响

后端只在 `notify_tpl_sms` / `notify_tpl_call` **为空**时才回落默认值。所以：

- **没动过**这两项的设备 → 升级后自动变成新文案；
- **自己写过**文案的设备 → 保持原样，不会被覆盖。

想把实机也换成新文案，把这两项清空即可：

```sh
uci -q delete at-webserver.config.notify_tpl_sms
uci -q delete at-webserver.config.notify_tpl_call
uci commit at-webserver
/etc/init.d/at-webserver restart
```

清空后由后端内置默认值接管，后续改文案只需升级包。

## 四、短信中心：会话改为聊天式单时间轴

上一版把会话拆成「收到的」与「发出的」两块分区。实际用下来分区反而割裂了对话的时间线 —— 一次来回被拆到上下两处，读起来要来回跳。本版改为**聊天式单时间轴**：

- 收发消息按时间**升序混排在同一条轴上**，靠气泡左右位置区分方向 —— **对方在左、自己在右**；
- 跨天处插入居中**日期分隔条**（形如 `2026-10-12`）；
- 日期既然由分隔条承担，**气泡内就只留时刻**，不再每条都重复一遍年月日；
- 没有发送时刻的发出短信**借存储顺序落回它该在的位置**，不再一律沉到会话末尾（原因见下）；
- 「删除」按钮改为**悬停显现**（触屏设备常显），不再让红色按钮盖过正文。

### 为什么「你一句我一句」一开始是不成立的

改完上面的排布，实际渲染出来却是「左、左、右」——对面两句挤在一起，自己那句跑到最后。查下去发现根子不在 CSS，而在**发出短信根本没有发送时刻**：

`3GPP TS 23.040` 里，SMS-SUBMIT 帧只带 TP-VP（有效期），**没有 TP-SCTS（发送时刻）**。收到短信的时间戳来自 TP-SCTS，一定有；而发出的短信只要模组把它存下来再读回去，时间就是真的不知道。于是它被归入「时间未知」并一律排到会话末尾，一次来回被打散。

**修法：借存储顺序，不伪造时刻。**

`AT+CMGL` 的序号就是存储先后。取该条**前面最近那条有确切时刻的消息**的时刻作锚点，让它落在那个位置附近：

```
存储序号 1  收到  明天上午的评审改到十点，方便吗？   00:48:56
存储序号 2  发出  方便，我九点半到会议室。           时间未知   ← 锚到上一条的位置
存储序号 3  收到  好，会议室在 3 号楼 502。          00:52:56
```

渲染出来就是 **左 → 右 → 左**，与真实对话一致。锚点只参与排序与日期分隔条的归属，气泡里照旧标「时间未知」—— 位置是推断的，时刻是未知的，这两件事在界面上必须分得清。

### 另一处：去重时把唯一带准确时间的记录丢了

同一会话的已发短信可能同时来自两处：模组存储（SMS-SUBMIT PDU）与浏览器 localStorage 缓存。原实现的原则是「模组是权威来源，冲突时丢缓存那份」—— 可**模组那份恰恰没有时刻**，缓存那份才是本机发送当时打的时间戳。丢掉缓存，等于把这条消息唯一的准确时间一并扔掉（这也正是上面那个问题的第二重来源）。

改为反向**吸收**：把缓存的时间戳补给模组那条。模组的 index 仍然保留 —— 删除要走 `AT+CMGD`，不能换成缓存的负数 index。

### 顺带修掉一个一直存在的视觉缺陷

气泡原先是「宽度不超过 80%」的**块级元素**。块级元素默认占满可用宽度，于是 `margin-left: auto` 这个右对齐手段**完全失效** —— 发出的消息贴不到右边，看上去与收到的没有任何区别。

改为 `width: fit-content` 之后，气泡宽度随内容收缩，`margin-left: auto` 才真正生效，左右分列成立。这不是新功能，是一个从有气泡起就一直错着的样式。

## 五、修掉「存储用量恒为 0 / 0」

### 排查过程

界面上的存储用量一直显示 `0 / 0`，但 SIM 卡里确实有短信。上一版怀疑是响应正则只匹配标准前缀 `+CPMS`，改成 `[\^+]CPMS` 收工。

实机验收时这个数字**仍然是 0 / 0**，于是直接看前端到底发了什么命令：

```
AT^CPMS?   → ERROR
AT+CPMS?   → +CPMS: "SM",0,50,"SM",0,50,"SM",0,50
```

### 真因

前端发的是**私有前缀**命令 `AT^CPMS?`，而本模组（MT5700M-CN）**不认私有前缀**，直接回 `ERROR`。响应正则再怎么兼容也没用 —— 请求本身就失败了。

同一项目的「短信设置」页用的**一直**是标准写法 `AT+CPMS?`，此处纯属笔误。

### 修复

- 请求改为标准 `AT+CPMS?`；
- 响应侧仍保留 `[\^+]CPMS` 双前缀匹配，兼容个别回私有前缀的固件；
- 回归用例**刻意让私有写法失败**，前端一旦退回 `^` 前缀，存储用量断言会立刻挂掉。

### 顺带修掉一个夹具缺陷：`AT^MONSC?` 多了一个问号

给模拟链路补信号巡检用例时才发现，巡检一直报的是 `RSRP -140 dBm`「极差 · 频发脱网」。

根因不在产品代码，而在夹具：模拟模组把服务小区查询写成了 `AT^MONSC?`（**带问号**），而后端 `urc::query_monsc` 与前端 `network_status.js` 发的都是 `AT^MONSC`（**不带问号**）。命令匹配不上，模组回落到 `AT^HCSQ?`，于是拿到一个恒为 0 的原始值、换算成 `-140 dBm`。

这个缺陷之所以长期没被发现，是因为**此前模拟环境从来没有真正触发过信号巡检** —— 假读数一直躺在那里没人看。补上用例后它立刻暴露。夹具现在两种写法都认，并在注释里写明命令名必须与后端对齐。

## 升级方式

```sh
# apk 系统（OpenWrt 25.x / ImmortalWrt SNAPSHOT）
apk add --allow-untrusted ./<ARCH>-luci-app-mt5700-1.14.18-r1.apk

# opkg 系统（OpenWrt 24.10 及更早）
opkg install ./<ARCH>-luci-app-mt5700_1.14.18_<ARCH>.ipk
```

升级后建议重启服务并清理 LuCI 前端缓存：

```sh
/etc/init.d/at-webserver restart
rm -rf /tmp/luci-modulecache /tmp/luci-indexcache
```

> 本版改动了前端 CSS 与 JS，**必须清 LuCI 缓存**，否则页面仍会执行旧脚本。
