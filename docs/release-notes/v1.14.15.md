# v1.14.15 发布说明

**v1.14.15 为通知链路修复与可配置化版本**：定位并修复「QQ 机器人推送未接入任何推送数据」的真实根因，新增可配置的推送频率与自定义推送文案模板，并清理全部推送文案中的插件名字样。**未触碰任何 IMEI 相关代码与数据流**。

## 一、「推送未接入任何数据」根因修复（核心）

### 症状

按推荐流程完成绑定（bind 模式）后，QQ 端**收不到任何业务推送**；手动点「发送测试通知」却又能收到消息。

### 根因

`Notifier::run()` 在任务启动时若判定「当前没有任何可用通道」就直接 `return`：

- 该任务的 `mpsc::Receiver` 随任务结束被丢弃 → 队列入口**永久关闭**；
- 此后 `notify()` 内部的 `try_send` 全部返回 `Closed` 并被忽略，**事件在入口就被静默丢弃**；
- bind 模式下用户完成绑定后，`set_qq()` 虽然热替换了发送器（通道变了），但**入口早已关闭** —— 于是「绑定成功却一条数据都收不到」。

测试通道能收到，是因为 `notify_test` 绕过队列直发，与业务推送不共用入口，所以掩盖了问题。

### 修复

1. **合并窗口任务恒定运行**：不再因「启动时还没有通道」而退出，`Receiver` 生命周期与进程一致。
2. **`dispatch_enabled()` 纳入绑定态**：把 `qq_bind_pending`（绑定模式等待绑定）也算作「可能送达」，事件继续入队；能否真正发出交由发送时刻判定。
3. **`flush_all` 无通道时保留队列**：原先会清空待发队列，现在保留并在绑定成功那一刻补发，做到绑定前后事件零丢失。

## 二、推送频率（合并窗口）可配置

- 新增 UCI `notify_interval`（秒），默认 **60**，双向夹取到 **5~3600**（越界自动纠正，不会出现 0 秒刷屏或超大窗口）。
- LuCI 服务配置页通知卡片新增「推送频率（合并窗口）」数字输入，附「窗口内多条事件合并为一条推送」说明。
- 实机验证：写入 `notify_interval='15'` 重启后，启动日志输出 `通知合并窗口: 15 秒（事件在该窗口内合并为一条推送）`。

## 三、自定义推送文案模板

新增 UCI 六项，留空即使用内置默认文案：

| 配置项 | 作用 | 默认值 |
|:--|:--|:--|
| `notify_tpl_prefix` | 全局前缀（每条推送首行） | 空 |
| `notify_tpl_sms` | 新短信 | `📱 新短信通知\n发送者: {sender}\n内容: {content}` |
| `notify_tpl_call` | 来电 | `📞 来电提醒\n{content}` |
| `notify_tpl_signal` | 信号变化 | `{content}` |
| `notify_tpl_memory` | 短信存储满 | `⚠️ 警告：短信存储空间已满\n请及时处理，否则可能无法接收新短信` |
| `notify_tpl_batch` | 批量汇总标题 | `📑 批量通知汇总` |

可用占位符：`{sender}` `{content}` `{time}` `{kind}` `{count}`；**未知占位符原样保留**，便于发现拼写错误。存储满事件正文为空时回落「短信存储空间已满」可读文本。

UCI 单个 option 不支持真实换行，模板中的换行以 `\n` 转义写入（LuCI 页面自动转换，手改 UCI 需自行写 `\n`；`\n` `\t` `\r` `\\` 均支持，未知转义原样保留）。

LuCI 侧新增「推送文案」卡片：6 个输入框 + 占位符说明 + 「恢复默认文案」按钮，内置默认值与 Rust 侧 `DEFAULT_TPL_*` 严格对齐。

## 四、推送文案不再出现插件名

- 「发送测试通知」：`[luci-app-mt5700] 测试通知：…` → **`测试通知：推送通道链路正常`**。
- 绑定成功确认消息：`[luci-app-mt5700] 绑定成功…` → **`绑定成功（QQ 号标签: xxx）：后续通知将推送到本会话`**。
- 验证：新二进制全量检索 `luci-app-mt5700` 命中数 **0**；实机出站文本日志确认为 `[MT5700 验证]\n测试通知：推送通道链路正常`。

## 五、出站文本可观测

合并推送与测试通道均记录**实际发出的文本**：

```
推送内容（合并 3 条）: [MyRouter] 18:20:31│📱 新短信通知…
推送内容（测试通道 qq）: 测试通知：推送通道链路正常
```

此前排障只能看到「QQ 机器人通知发送成功」，无法得知模板究竟渲染成了什么。**提示**：内存日志缓冲上限 1200 条且会被 AT 指令追踪日志快速占满（页面开启轮询时数分钟即滚完），事件发生后请立即查看日志页。

## 六、验证

- `cargo test` **56 passed / 0 failed / 2 ignored**；`node --check` 前端改动全部通过。
- 新增回归用例 `merged_push_renders_template_and_posts_to_webhook`：本地 TCP 监听模拟 WebHook 接收端，断言「事件 → 入队 → 合并窗口 → 模板渲染 → HTTP 投递」整条链路**真正发出的报文内容**（含全局前缀与全部占位符）。若 `run()` 再被改为「启动时无通道就退出」导致事件无法入队，该用例会超时失败而不会静默放过。
- `cargo zigbuild --release --target aarch64-unknown-linux-musl` 交叉编译通过；实机（ImmortalWrt SNAPSHOT / mediatek filogic / aarch64_cortex-a53）部署后 md5 一致、服务正常重启。
- 实机全链路：测试通道 HTTP 200 送达且文案无插件名；合并窗口时长、全局前缀、事件模板三项配置均在生产链路真实生效。
