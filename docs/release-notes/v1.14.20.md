# v1.14.20

**主题**：推送频率（合并窗口）改为**定时推送间隔**，单位从**秒**换成**分钟**；到点就推一次当前实际情况，不再攒批合并。

## 改了什么

| 项 | 旧 | 新 |
|:--|:--|:--|
| UCI 键 | `notify_interval` | `notify_timer_interval` |
| 单位 | 秒 | **分钟** |
| 取值范围 | 5 ~ 3600 秒 | 1 ~ 1440 分钟（1 分钟 ~ 24 小时） |
| 默认值 | 60 秒 | **10 分钟** |
| 语义 | 攒一批一起发；窗口内无事件则一条都不发 | **到点就发一条**，推的是此刻真实状态 |
| 短信 / 来电 | 实时直发 | 实时直发（**不受影响**） |

旧键 `notify_interval` 无需手工处理：后端 `secs_to_timer_minutes()` 会把它向上取整换算成分钟，前端保存时写新键并把旧键置空。

> **升级到 v1.14.21 更稳妥**：本版对旧键一视同仁地按公式换算，于是**出厂默认值 60 秒会变成 1 分钟** —— 而包内配置原本就写死 60，绝大多数设备上它代表「用户从没改过」。v1.14.21 起改为：60 秒落到新默认值 10 分钟，被改过的值才按公式换算。详见 v1.14.21 发布说明。

## 三条推送线，各管一件事

| 线 | 触发 | 内容 | 配置项 |
|:--|:--|:--|:--|
| 短信 / 来电 | 模组 URC（`+CMTI` / `RING`）一到就发 | 单条事件 | 无（始终实时） |
| 信号巡检 | 时段内按间隔采样，命中变化才发 | 突变事件 + 完整射频评估 | `notify_poll_*` |
| **定时推送** | 每 N 分钟**必定**发一次 | 当前状态快照（信号读数 + 存储占用） | `notify_timer_interval` |

巡检与定时推送**并存互不影响**：巡检抓突变，定时推送做保底 —— 让你确认链路还在。只想保留突变通知，把间隔拉到 1440 分钟（24 小时）即可近似关闭定时推送。

## 权衡：间隔怎么选

- **调小**（最小 1 分钟）：状态更新鲜，但推送条数线性上升。QQ 官方主动消息频控为**单关系 20 条/分钟、群 30~60 条/分钟、1000 条/群/天**，1 分钟间隔即每天 1440 条，会撞上限。
- **调大**（最大 24 小时）：几乎不打扰，但**两次之间发生的变化要等到下一个整点才被看到**，且单次推送承载的内容更多（状态快照含信号与存储两块），读起来更费劲。
- **建议 5 ~ 30 分钟**，默认值 10 分钟即取此区间。

默认为什么从 60 秒改成 10 分钟：定时推送**每轮必发一条**，若沿用 60 秒就是每天 1440 条，远超频控；10 分钟为每天 144 条，是「状态新鲜」与「不刷屏」之间的平衡点。

## 定时推送为什么自己现读状态

- 本模组**不会主动上报**信号（实机 1200 条 AT 记录里 `^HCSQ` / `^CERSSI` 自发上报为 **0 条**），信号只有主动查询才是真的；
- 存储满的 `^SMMEMFULL` **只在恰好收满那一刻来一次**，此后即便清理过也不会再来 —— 沿用旧状态会一直卡在「已满」。

因此定时推送每轮都发 `AT^HFREQINFO?` / `AT^MONSC` / `AT+CPMS?` 现读一次。采样函数与信号巡检**完全复用**（`sample_signal()` / `band_label()`），两条线同一口径。

边界处理：

- 采样不到就**明说「暂无读数」**，不拿上一轮的旧值冒充当前状态；
- 存储容量读到 0 视为**没读到**而不是「满了」；
- 总开关关闭 / 模组未连接 / 长命令（扫频）进行中 → 跳过本轮，一条 AT 都不发；
- 首轮**先睡满一个间隔**再推 —— 开局立刻采样往往只能拿到空读数。

## 推送长什么样

```
🕒 当前状态（定时推送）
时间：2026-10-12 02:30:00

📶 5G · n41 · 2565 MHz / 100 MHz
RSRP -62 dBm  极佳 · 满格服务
SIGNAL 100%  极佳 · 满格服务
网络能力：优秀 —— 当前网络能力优秀…

💾 短信存储 3 / 50
```

存储满时会写成 `💾 短信存储已满（50 / 50）—— 清理前可能收不到新短信`，把后果一并说清。

## 一个副作用：批量汇总标题进入休眠

攒批合并移除后，生产路径**逐条直发**，`notify_tpl_batch`（批量汇总标题）与 `{count}` 的「多于一条」分支不再会被触发。模板、占位符与单测都保留 —— 已自定义的配置不会丢，日后若出现「一批事件一起推」的场景可直接复用。LuCI 页面在该项下标注了「保留仅为兼容，当前不会被触发」。

顺带清理了「合并窗口」的遗留说法，其中两条是**用户可见**的：

- `channel=signal` 的拒绝理由原为「其余走合并窗口」，现改为「信号请等定时推送或真实巡检」；
- 启动日志原为「其余按合并窗口批量发送」，现改为「均实时直发，另有定时推送按间隔推送当前状态」。

## 升级

```sh
# apk（ImmortalWrt / OpenWrt 24+）
apk add --allow-untrusted ./<ARCH>-luci-app-mt5700-1.14.20-r1.apk

# opkg
opkg install ./<ARCH>-luci-app-mt5700_1.14.20_<ARCH>.ipk
```

升级后配置**自动迁移**，无需手工改动；如需确认：

```sh
uci show at-webserver.config | grep notify_timer_interval
# at-webserver.config.notify_timer_interval='10'
```
