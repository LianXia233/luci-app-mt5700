# v1.26.1

**主题**：把短信收发链路放到**同型号模组的实机固件**上逐条对照，修掉 7 处行为缺陷，并新增一份只讲协议与命令的参考文档。参照物不再是 AT 手册或上游 WebUI 的打包产物，而是 `192.168.88.1`（Hiveton-H5000M + MT5700M-CN）上那份**真跑得通**的实现：`controller/modem.lua` + `/usr/bin/smssend` + `/usr/bin/pdul.lua` + `/usr/bin/pdu_decoder` + `/usr/bin/sendat`，全部 md5 校验后取回。

---

## 1. 为什么这一版只对着实机改

v1.26.0 把短信链路重构成"一次 RPC 一个语义动作、后端单事务独占通道"，方向是对的，但它的每一处细节都来自**手册与厂商 bundle 的静态推断**。这一版把同样的问题重新问了一遍："这台机器上真正发得出短信的那份代码是怎么写的？"——结果七处里有五处的答案与我们的实现不同。

真机证据只有一条，也是唯一被允许的一条：

```
POST admin/modem/smssend number=10000 text=102
→ {"ok":true,"number":"10000","toa":"81","segments":1,"refs":[19]}
随后 admin/modem/smslist 里那条 10000 的短信 stat 由 0 变 1
```

`toa:"81"` 直接证明了特服短号该按国内格式编码；`stat` 变化证明了"读列表本身就把模组里的标记洗成已读"。其余结论一律来自读实机代码 + Rust 侧 mock 模组复现，**没有一条靠"真机发过所以应该没事"**。

## 2. 七处修正

| # | 缺陷 | 实机的答案 | 后果 |
|:--|:--|:--|:--|
| 1 | `index == 0` 被当成"没有序号"，`delete` 顺手把 0 挡掉 | 实机 `smslist` 回的就是 `"indices": [0, 1]` —— **0 是真槽位** | 卡上**最老的那条短信在界面上永久删不掉**。序号类型改为 `Option<u32>`：读不出 = `None`（界面禁用勾选并提示"不在模组存储中"），0 照删 |
| 2 | 批量删除按升序逐槽下发 | 厂商 `action_smsdel` 排序后**倒着**逐条 `AT+CMGD`。注释原话："一条命令一个槽位：模组不收槽位列表。从大到小删，免得剩下的槽位号在中途挪位" | 升序删到一半，剩下的槽位号可能已经指向别条短信 —— 删错东西 |
| 3 | 收件人号码照用户输入的写法直接编码 | `smssend.normalize()` 四档判定：剥空白与 `-()`；`+`/`00` 开头算国际；**裸的 11 位 `1` 开头手机号补 `86` 按 0x91**；其余短号与固话按国内 0x81 | 界面上填 `13800138000` 会以国内格式发出，与实机在网侧的写法不一致。新增 `pdu::normalize_destination()` 与其完全对齐 |
| 4 | 提交片失败后直接继续用端口 | `smssend` 拿不到 `+CMGS` 时第一件事是 `at("\x1b", 3)` | 模组可能停在"等 PDU"的**半开输入态**，紧跟着的 `AT+CPMS?` 会被当成 PDU 吞掉 —— 一次发送失败连带把后面的读写一起拖死 |
| 5 | `+CMTI` 上报里的存储区名解析出来就丢掉，直接 `AT+CMGR=<index>` | `<index>` 是"当前 `<mem1>` 里的第几格"（手册 8.1.1），两个区各自从自己的 0 号位排起 | `+CMTI: "SM",7` 落在 `mem1="ME"` 时读到的是模组 FLASH 第 7 格**另一条**短信，还顺手把那条标成已读 —— 推给用户的正文与真实新短信毫无关系 |
| 6 | 清空短信后 `mem1` 停在最后试过的区上不还 | 实机的清空压根不切区（一条 `AT+CMGD=0,4` 清当前 `mem1`），所以没有这个副作用 | "清空短信"这一个动作连带改掉了之后所有 `list`/`delete`/`CMGR` 的默认介质，用户看到列表莫名其妙换了一个区 |
| 7 | `delete` 从来没上短信超时表 | —— | 走默认 12s，而后端最坏是 排队 10s + 每槽 2s + 回读 2s，**删一条两段长短信就已经超预算**；被 `nc` 掐断的那次还会打开"后端不可用"的共享熔断，别的页面跟着 15s 全部快速失败。补 ucode `delete: 40` / 前端 `42000`，并把批量删除按 8 槽一批分批（`SMS_DELETE_CHUNK`），半途失败也回读一次列表 |

另外两处是同一次对照里顺出来的：

- **TP-VP 默认值纠正为 `0xA7`**。上一轮记的"0xA8 正好 24 小时"是**读歪了表**：144～167 档的偏移是 `n−143` 而不是 `n−144`，168～196 是 `(n−166)×1 天` —— 并不存在"1 天 + (n−168) 小时"这一档。所以 `0xA8` 实为 **48 小时**，24 小时是 `0xA7`，顺带与厂商 WebUI 用的是同一个字节。相邻档连续性自查：143→12h、144→12.5h、167→24h、168→48h、196→30 天、197→35 天。
- **首字节注释更正**：`0x20` 是 `bit5` 的 **TP-SRR（向网络索要状态报告）**，不是 `bit2` 的 TP-RD(`0x04`)。**这一位没有动** —— 现状意味着每条短信都会产生回执，配合 `AT+CNMI` 的 `ds=2` 会把回执存进 MT，是"存储比预期快满"的可疑来源之一。改它会影响在网行为，属产品决定，因此只更正注释并列入待真机确认项。

## 3. 两处「实机那么干、本插件不这么干」是故意的

1. 厂商 `pdul.lua` 一律 UCS2、每段固定 60 字（`sendLimit = 60 * 4` 个十六进制字符）；本插件按 GSM 03.38 自动在 7bit/UCS2 里挑，分片用规范的 160/153 与 70/67 —— 更省也更符合 23.040。
2. 厂商发短信总把短信中心写成 0 长度（用卡里存的 CSCA）；本插件读 `AT+CSCA?` 编进 PDU，为的是"在短信设置里改过中心号"当场生效。

也记一笔**厂商自己的边界缺陷**：`pdul.lua` 在正文**恰好**等于上限时置了 UDHI 却不写 UDH 头，接收方会吞掉正文头 6 字节；`smssend` 靠 `fix_udhi()` 事后把那一位抹掉。本插件的编码器只在真的分片时才置 UDHI，不存在这一格。

## 4. 新增《短信链路协议与命令参考》

[`docs/sms-at-protocol.md`](../sms-at-protocol.md) —— 只讲协议与命令，不讲界面操作：

- 传输层对照：实机 `sendat`（自动探 AT 口 + `/tmp/sendat.atport` 缓存 + `flock` + 19200 raw + 以 `OK`/`ERROR`/`+CME`/`+CMS` 收尾）对 本仓库的串口 + 事务租约；
- `AT+CNMI=2,1,0,2,0` 五个参数逐个解释为什么不取别的值；
- `AT+CMGL=4` 的四个陷阱：只列当前 `mem1`、已发短信也在里面且字段布局不同、**读即已读**（9.8.2）、判据是 `OK` 而不是"有没有条目"；
- SMS-SUBMIT 首字节位表、PDU 逐字段、长度字段算法、UDH 在 7bit 下要 `align_to(7)`；
- 一次性 `AT+CMGS=<len>\r<PDU>`（分隔符是**字面的反斜杠 + r**）与两段式回退的判据矩阵，附同一台模组的实测对照；
- `delflag` 表、三层超时预算对照、命令速查总表、串口手工复现步骤与**已核对过的报文**。

面向用户的《短信功能使用文档》按约定**不随仓库发布**，因此 README 与上述文档的入口一律只指向协议参考。

## 6. 遗留实机验证项

1. `AT+CEUS` 的目标值方向：本插件开短信写 `CEUS=1`，厂商 WebUI 写 `CEUS=0` 且时机在 `CFUN=0` 之后。手册通篇没把 `CEUS` 与短信/IMS 绑定，属推断。
2. `AT+CFUN=0/1` 是否足以让 `CEUS` 生效（手册只说"需要开关机生效"）。
3. TP-SRR=1 的实际后果：网络侧是否因此往 MT 里写状态报告并加速 `^SMMEMFULL`。
4. 半开输入态下模组认不认裸 ESC(0x1B) —— 这一条是照厂商脚本的姿势补的，缺一次仪器级观察。
5. `+CMTI` 报的区与当前 `mem1` 不一致在现网有多常见，决定第 5 处修复的覆盖面。

## 7. 升级方式

从 [Releases](https://github.com/LianXia233/luci-app-mt5700/releases) 下载对应架构软件包覆盖安装即可，配置与存储格式向后兼容，无需手工迁移。

装上后建议按这个顺序自测（**只允许向 `10000` 发送内容 `102`**）：短信设置页确认两个开关 → 短信中心刷新列表看容量条是否稳定 → 勾选**最老那条**（槽位 0）删除，验证不再"删不掉" → 发一条 `102 → 10000` → 再发一条长短信，观察分段是否齐、回执是否把存储撑满。
