# 短信链路协议与命令参考（MT5700M-CN）

本文只讲**协议与命令**：发送、接收、读取（列表）三条链路各下发什么 AT、
字段怎么编、应答怎么判、超时怎么算。界面行为与提示文案以
[`sms_center.js`](../htdocs/luci-static/resources/view/at-webserver/sms_center.js)
与 [`sms_settings.js`](../htdocs/luci-static/resources/view/at-webserver/sms_settings.js)
的页头注释为准，这里不重复。

取证来源分两栏并排写清：

- **实机**：内网测试机上厂商自己的实现 —— `/usr/bin/sendat`、`/usr/bin/smssend`、
  `/usr/bin/pdul.lua`、`/usr/bin/pdu_decoder`、`/usr/share/modem/smsc.sh`、
  `/usr/share/luci/menu.d`+`modem.lua`（均 md5 校验后取回，存档在会话目录 `device-ref/`）。
- **本仓库**：`src/rust/src/{pdu,sms,urc,atclient,serial_linux}.rs` 与前端 `sms_center.js`。
- **手册**：鼎桥 MT5700M-CN AT 手册章节号（8.x／9.x），与 3GPP TS 23.038／23.040／27.005 的
  通用定义一并标注。手册与规范冲突时以实机表现为准，并在文末「待真机确认」列出。

> **测试边界**：真机只允许向 `10000` 发送内容 `102`。本文所有其它报文形态
> 均由编码器生成、经解码器回读验证，未向任何真实号码下发。

## 1. 传输层：命令怎么送达模组

短信的一切语义都建立在"独占 AT 通道"之上，所以先把通道层写清楚。

### 1.1 实机：`sendat`

| 环节 | 实际做法 |
|---|---|
| 找端口 | 遍历 `/dev/ttyUSB*` + `/dev/ttyACM*`，对每个发裸 `AT`（1.2s 超时），**第一个回 `OK` 的**就是 AT 口；命令行里的 `<index>`（一般传 `1`）只当优先猜测用的提示 |
| 记住端口 | 结果写 `/tmp/sendat.atport`；后续调用直接读缓存，读到空应答时重新探测并**换端口重试一次** |
| 互斥 | `flock /tmp/sendat.at.lock` 独占，最多等 8s，等不到就**不持锁继续发**（best-effort，注释里明说了这是在赌运气） |
| 线路参数 | raw 19200 8N1：`iflag/oflag/lflag = 0`，`cflag = CS8|CLOCAL|CREAD`，清 `PARENB`/`CSTOPB`，`VMIN=0 VTIME=0`，打开后先 `tcflush(TCIOFLUSH)` |
| 收尾 | 命令文本后追加 `\r\n` |
| 判结束 | 累积应答，直到 rstrip 后以 `OK` 或 `ERROR` 结尾，或中间出现 `+CME ERROR` / `+CMS ERROR` 即停 |

厂商 Web 页的老通道 `smsc.sh` 是这个形状：

```sh
sendat "$1" "$2" >/dev/null 2>&1   # $2 是页面传来的任意 AT 命令（裸 AT+CMGD=x / at+cmgl=4）
sendat 1 at+cmgl=4 | pdu_decoder --list > /tmp/smsc.at
```

也就是说旧页面**先把动作命令裸下发、再无条件重读整份列表**，把结果渲染成文本块
（`/tmp/smsc.at`，读完即删）。新页面（`action_smslist`）改成了 `pdu_decoder --json`，
因为文本块塞不下已读/未读标志位。

### 1.2 本仓库：常驻 daemon 的 AT 客户端

| 环节 | 实际做法 | 位置 |
|---|---|---|
| 找端口 | 分层取候选：`/dev/serial/by-id/*` 优先 → USB 类 `ttyUSB`/`ttyACM`/`ttyAP` 回退 → 完全没有 USB 串口时才用 SoC 串口 `ttyS`/`ttyAMA`；按 `port_rank` 排序后由 `MAX_PROBE_CANDIDATES` 截断到 **10 个**，逐个发裸 `AT`（`AT_PROBE_TIMEOUT` = **800ms**），**第一个回 `OK` 的**即 AT 口。**与 §1.1 的 `sendat` 是两套独立实现，数值不要互抄** | [serialdetect.rs:373](../src/rust/src/serialdetect.rs#L373)、[serialdetect.rs:33](../src/rust/src/serialdetect.rs#L33)、[serialdetect.rs:38](../src/rust/src/serialdetect.rs#L38) |
| 打开端口 | `open(O_RDWR\|O_NOCTTY\|O_NONBLOCK)`；`CS8\|CREAD\|CLOCAL`，无校验、单停止位 | [serial_linux.rs:153](../src/rust/src/serial_linux.rs#L153)、[serial_linux.rs:52](../src/rust/src/serial_linux.rs#L52) |
| 读阻塞语义 | `VMIN=1`（**不能用 0**：Linux tty 在 `VMIN=0/VTIME=0` 下"暂无数据"的 `read` 返回 0，会被当成 EOF 而误关端口） | [serial_linux.rs:56](../src/rust/src/serial_linux.rs#L56) |
| 排队 | 单一队列 + 优先级；短信动作走 `AtPriority::Sms`，**排在后台信号轮询之前** | [at_queue.rs](../src/rust/src/at_queue.rs) |
| 事务 | `open_sms_transaction(ctx, "sms.list", 10s)` 取得一次独占租约；期间其它命令拿不到通道 | [sms.rs:302](../src/rust/src/sms.rs#L302) |
| 前台租约 | 短信页活跃时给模组"短信模式"续租 90s（上限 `SMS_MAX_LEASE`），避免被采集任务反复抢占 | [sms.rs:38](../src/rust/src/sms.rs#L38) |
| 错误码 | 启动时 `AT+CMEE=2`（详细错误文本），否则失败只回 `ERROR`，无从判断 | [atclient.rs:412](../src/rust/src/atclient.rs#L412) |

**两边最大的结构差别**：`sendat` 每次调用都重开一次串口、靠文件锁串行化；本仓库是一个
长驻进程持有端口，靠事务与租约串行化。这带来一个实机没有的约束——**主动上报（URC）
会混进正在等待的那条命令的应答行里**，所以本仓库必须显式识别 `+CMTI`／`+CDSI`／
`^SMMEMFULL` 并把它们从命令应答里摘出去（见 [urc.rs](../src/rust/src/urc.rs)）。
`sendat` 每次只看一条命令的短窗口，撞上了也就是那一次应答多几行。

## 2. 会话前置：模组侧的开关与参数

这些命令不属于三条链路本身，但缺任何一条，链路就会以看似无关的失败收场。

### 2.1 参数设置（开机/重连时）

| 命令 | 值 | 为什么是这个值 |
|---|---|---|
| `AT+CMEE=2` | 详细错误码 | 手册与 27.005 都定义 0=关／1=数字／2=文本；取 2 才能把 `+CME ERROR: memory full` 这类原因显示出来 |
| `AT+CNMI?` → `AT+CNMI=2,1,0,2,0` | 见 §4.1 | 手册 8.3.4 写明**掉电不保存**，8.3.2 更直接：MT 重启后 `CNMI` 回到 `0,0,0,0,0` —— 那样一条 `+CMTI` 都收不到，所以每次连接必须重设 |
| `AT+CMGF?` → `AT+CMGF=0` | PDU 模式 | 厂商 Web 页在读列表前会把它切回文本模式供自己用；**文本模式下把编码好的 PDU 当字符串发出去，就是一条乱码短信**（`smssend` 注释原话） |

`AT+CNMI` 只在查询应答不含 `2,1,0,2,0` 时才重设；`AT+CMGF` 只在**确认已经是 0** 时才跳过。
设置命令必须显式检查 `OK`，否则"模组拒绝"会被静默吞掉。
（[atclient.rs:418-447](../src/rust/src/atclient.rs#L418)）

### 2.2 短信能力开关（用户在"短信设置"页点一次，不是每条短信前）

开启的真实序列（[sms.rs:851-1005](../src/rust/src/sms.rs#L851)）：

```
AT+CEUS?                      -- 先读；已经是 1 就整段跳过射频重启
AT+CEUS=1                     -- 需要改才写；必须在 CFUN=0 之前
AT+CFUN=0                     -- 关射频
   （等待 ≥ 1.1s，CFUN_SWITCH_GAP）
AT+CFUN=1                     -- 恢复射频（单条预算 10s）
   轮询 AT+CFUN? / AT+CEREG?  -- 确认射频与注册真的回来了
AT^IMSSWITCH=1,0,0            -- 开 LTE IMS
AT+CSCA="<短信中心>"           -- 可选，用户填了才写（手册 9.5.4：掉电保存，写一次即可）
```

关闭**只下发** `AT^IMSSWITCH=0,0,0`：不动射频、不改 `CEUS`、不清空短信。

三点必须写进协议口径：

1. `CEUS` **要经一次开关机才生效**（手册 3.15.2），所以写过它就必须重启射频；
   反过来 `CEUS` 已经是 1 时整套重启都是白断网 —— 因此"先读再决定"。
2. `AT^IMSSWITCH` 需要在**上电初次开机后**才能设置（手册 4.10.2）。刚恢复射频时它
   可能仍拒绝，所以放在序列末尾再试一次。
3. **厂商 WebUI 的方向与这里相反**：它开启短信时下发 `AT+CEUS=0`（语音中心）、
   关闭时下发 `AT+CEUS=1`（数据中心），而且是在 `AT+CFUN=0` **之后**才写 `CEUS`。
   手册通篇（3.15／4.10）都没把 `CEUS` 与短信/IMS 绑定，1 还是 0 属推断。
   → 见 §9 待确认项。

## 3. 读取短信（列表）

### 3.1 命令序列

**实机**（`modem.lua:action_smslist`）：

```
sendat 1 at+cmgl=4 20 | pdu_decoder --json        # 列表，20s
sendat 1 'AT+CPMS?' 5                             # 容量，5s
```

**本仓库**（[sms.rs:296-367](../src/rust/src/sms.rs#L296)）：

```
AT+CMGF?            2s    ┐ 已确认是 0 才跳过
AT+CMGF=0           2s    ┘ 查询失败/看不懂 → 一律强制设一次（幂等，代价远小于模式歧义）
AT+CMGL=4          25s
（同一次事务内）AT+CPMS?  2s   → 存储用量
```

`list()` 与 `capacity()` 是**两个独立事务**（本仓库），实机则是两次独立 `sendat`；
共同点都是"一次真实下发"，绝不读缓存 —— 因为 `AT+CMGL` 的结果会随新短信、删除、
换区实时变化，缓存过的 index 拿去删除会**全部回 ERROR**（[sms.rs:296](../src/rust/src/sms.rs#L296)）。

### 3.2 `AT+CMGL=4` 的语义

| 点 | 内容 |
|---|---|
| 参数 | `stat` 过滤：0=REC UNREAD、1=REC READ、2=UNSENT、3=UNSENT&READ-REPLY、4=全部（手册 9.8.1／27.005） |
| 应答形态 | 若干组「`+CMGL: <index>,<stat>,,<length>` 头行 + 一行 PDU hex」，以 `OK` 收尾；失败形态是 `+CMS ERROR: <err>` |
| **只列当前 `<mem1>`** | `AT+CPMS` 的首选存储器决定读哪个区（手册 8.1.1）。所以"短信少了几条"要先怀疑区，而不是怀疑丢数据 |
| **已发短信也在里面** | `=4` 会把存下来的 **SMS-SUBMIT** 一起列出来。它和 SMS-DELIVER 的字段布局不同（多一个 TP-MR、少一个 SCTS），**按 DELIVER 解会整条错位** —— 号码、时间全错。实机的 `pdu_decoder` 正是"一律按 DELIVER 解"，所以它的已发短信列不可信；本仓库按 TP-MTI 分派（[pdu.rs:402-509](../src/rust/src/pdu.rs#L402)） |
| **读即已读** | 手册 9.8.2：`AT+CMGL` 只要把"收到的未读短信"列出来，存储里的状态就**同时变成"收到的已读"**。列一次 = 全部标记已读 |

### 3.3 "空列表"与"读不出来"必须分开

判据是**有没有 `OK`**，不是有没有 `+CMGL` 行（[sms.rs:331-339](../src/rust/src/sms.rs#L331)）：

```rust
if !resp.ok() { return Err(...) }   // 没有 OK 就别当成"存储区是空的"
```

SIM 卡未就绪、AT 口竞争失败、模组忙，给出的都是"零条目 + 没有 OK"。把它洗成
"本机没有短信"，用户下一步就会去删那些根本不存在的东西。
只判 `ok()`、不判 `has_error()`：`^SMMEMFULL` 那类附带 `CMS ERROR` 字样的上报行会混进
同一次应答，那时候列表其实已经完整读出来了。

实机 `pdu_decoder --json` 用的是同一条判据：`ok = any(line == "OK")`，
注释写得比这里还直白 —— *"空 SIM 和坏掉的 AT 口都给出零条短信，只有第二种是错误"*。

### 3.4 已读/未读标志：实机与本仓库的分歧（重要）

`pdu_decoder --json` 把 `stat` 直接透传（`stat = min(各段的 stat)`，缺字段则记 1），
并额外带 `indices`（一条长短信的多个槽位）。**但同一份文档链路上这标志不可信**：
每次刷新都是 `AT+CMGL=4`，等结果回到界面，`stat` 已经被这次读取翻成 1 了。

所以本仓库界面层的口径是（[sms_center.js](../htdocs/luci-static/resources/view/at-webserver/sms_center.js)）：
不拿模组标志位冒充持久未读，"未读"按「最新一条是收到的、且本次页面会话里还没点开过」估，
刷新即重置。协议层保留 `stat` 原样上报，语义解释放在界面层。

### 3.5 逐字段解码

`+CMGL` 头行：

| 字段 | 处理 |
|---|---|
| `<index>` | 解析失败 → **`None`，条目仍然保留**并带 `error` 显示（"不在模组存储中"）。绝不能把读不出的序号当 0 —— 那是别的短信的槽位 |
| `<stat>` | 透传；模组省略时按已读处理 |
| `<oa-ai>`（第 3 参，文本模式才有字母发件人；PDU 模式为空）与 `<length>`（第 4 参） | 都忽略：PDU 行本身完整给到，不靠长度截断 |

PDU（SMS-DELIVER）：

```
（存储里的 PDU 本身不带任何长度前缀，直接从 SCA 长度字节走）
SCA 长度(1) + SMSC 地址(TOA + BCD)
TP-MTI/UDHI 首字节      MTI = first & 0x03；UDHI = first & 0x40
TP-OA 地址              长度(1) + TOA(1) + BCD((len+1)/2)；字母型 TOA(0x50) 按 7bit 解
TP-PID(1)              跳过
TP-DCS(1)              编码方案，见 §3.6
TP-SCTS(7)             半字节交换的 YY MM DD hh mm ss + 时区
TP-UDL(1) + TP-UD
```

- **SCTS 时区**：本仓库解析它并折算到本地时区显示（含闰秒/半小时偏移的 15 分钟粒度）；
  实机 `pdu_decoder` **整个丢掉时区字节**，直接按模组给的墙上时间显示 —— 这是两处
  读数差 8 小时的来源。
- **无 SCTS 的已发短信（SUBMIT）**：协议里没有发送时刻，本仓库按 TP-VPF 判断字段长度，
  绝对/增强格式（7 字节 TP-VP）时拿来近似当发送时刻并标 `time_approx`；
  相对格式（1 字节）时根本没有时间，`time = None`。
- **发出记录的时刻由插件自己盖章（v1.27.0 起）**：既然模组给不出，就只能由后端在
  `outcome == Accepted` 的那一刻取 `crate::nettime::now()` —— 全仓库唯一墙上时间入口，
  **NTP 校时结果优先**，取不到才回退设备时钟。格式 `%y/%m/%d,%H:%M:%S`，与前端
  `archiveKey` 同格式、可直接对齐。`time_approx` 不再是「一律 true」，而是如实反映
  **这一次**的来源：`time_approx = !crate::nettime::from_ntp()` —— NTP 已同步时为
  `false`（与服务器同源，界面按精确时刻显示）；刚开机还没拨上号、NTP 不可达时仍为
  `true`（断电重启后设备钟可能停在 1970 或出厂时间，必须继续标「（近似）」）。
  前端 `sentTimeAnchor()` 因此**优先采用归档时刻**，模组 `AT+CMGS` 回读的那份只用于
  保留槽位 `index`（删除要靠它）。

### 3.6 TP-DCS → 编码（读侧）

DCS **必须按 bits 7-4 先分组**，字符集在每组里的位位置不一样（本仓库
`resolve_encoding`，[pdu.rs:85-111](../src/rust/src/pdu.rs#L85)）：

| DCS bits 7-4 | 组 | 字符集怎么取 |
|---|---|---|
| `0x0`–`0x3` | 通用数据编码组 | `(dcs >> 2) & 0x03`：`00` GSM7、`01` 8bit、`10` UCS2、`11` 预留（按 GSM7）；bit5 是压缩位，不参与字符集判定 |
| `0xC`、`0xD` | 消息等待指示组 | bit2：`0` GSM7／`1` UCS2 |
| `0xE` | — | UCS2 |
| `0xF` | 消息类别组 | bit3：`0` GSM7／`1` 8bit；bits1-0 是类别 0–3 |

> ⚠ 对全部 DCS 一律算 `(dcs >> 2) & 0x03` 是错的：`0xF5`（类别 1 的 **7bit** 短信）会得 1、
> 被判成 8bit，整列乱码。本仓库踩过这个坑，`resolve_encoding_handles_message_class_dcs`
> 钉住它（[pdu.rs:1223](../src/rust/src/pdu.rs#L1223)）。
> 实机 `pdu_decoder` 正是**不分组**的那一种（`coding = (dcs >> 2) & 0x03`，
> 2→UCS2、1→latin-1、其余 7bit），所以它读类别组 DCS 的短信会解错。

发侧只需三档：GSM7 → `0x00`、UCS2 → `0x08`、8bit → `0x04`
（[pdu.rs:1018-1022](../src/rust/src/pdu.rs#L1018)）。

7bit 是 **LSB-first 打包**，不是按字节查表；扩展字符用 `0x1B` 转义（`^ { } \ [ ~ ] | €`）。
本仓库与实机 `pdu_decoder` 的扩展表一致；`GSM_BASIC` 表内 `0x00` 起 80 项，越界回 `?`。


### 3.7 长短信聚合（分段 → 一条）

UDH 里两种参考号宽度都要认（[pdu.rs:601-619](../src/rust/src/pdu.rs#L601)）：

| IEI | 长度 | 字段 |
|---|---|---|
| `0x00` | 3 | 8 位参考号、总段数、当前段号 |
| `0x08` | 4 | **16 位**参考号（大端）、总段数、当前段号 |

实机 `pdu_decoder` 的聚合规则（`collect()`／`merge()`）：

1. 分组键 = `(发件人, ref)`；**`ref is None` 的段落单独成组**（不并成一条）。
2. 段内按 `seq` 排序后拼接文本 —— 注意它用 `x["seq"] if x["seq"] else 1`，
   **段号为 0 的段会被当成第 1 段**（真实网络侧几乎不出现，但从存储里读旧短信时可能）。
3. 组间按 `min(indices)` 排序 → **最旧的槽位决定顺序**，不是按时间戳。
4. 时间戳取组内第一个非空 SCTS。
5. `total` 取 `items[0]["total"] or len(items)` —— **段没收全也报已收段数**，
   界面上"1/3"这种残缺状态在实机侧是不区分的。

本仓库把条目原样交给前端，由 `sms_center.js` 按 `(number, reference)` 聚成会话；
"分段未收齐"在界面显示为部分消息而不是静默丢段。

## 4. 接收：一条短信进来了

### 4.1 上报模式：`AT+CNMI=2,1,0,2,0`

手册 8.3.3 五参 `mode / mt / bm / ds / bfr`：

| 参数 | 值 | 语义与取值理由 |
|---|---|---|
| `mode` | **2** | 短信通知与状态报告**直接送 TE**；送不出去时（如 online data 模式）先缓存在 ME，能发了再一次性补上。约束：`mode=0/2` 时 `<mt>` 不能取 2/3、`<ds>` 不能取 1，配错模组直接报错 |
| `mt` | **1** | 短信**存在 MT 里**并上报 `+CMTI: "<mem>",<index>`（手册 8.4）。这是列表/删除/容量都以"存储里的真实条目"为前提的形状；`mt=2/3` 是把 PDU 甩成 `+CMT` 且**不落盘**，界面就没有可删的条目了 |
| `bm` | **0** | 小区广播（CBS）不上报，本插件不处理 CBM |
| `ds` | **2** | 状态报告存在 MT 里并上报 `+CDSI: "<mem>",<index>`（手册 8.5）。内容界面暂不展示，但**必须被认成主动上报**，否则它会混进正在等待的那条命令的应答行里 |
| `bfr` | **0** | 从 `mode=0` 切到 1/2 后，把之前缓存的通知**一次性发给 TE**；取 1 才是清空丢弃，那样断连期间来的短信用户就永远看不到了 |

### 4.2 `+CMTI` 之后怎么读——本插件此前最严重的坑

```
+CMTI: "SM",7
```

| 事实 | 依据 |
|---|---|
| `<index>` 是**该存储区内**的序号 | 手册 8.1.1／9.9.1：每个区各自从自己的 0 号位排起 |
| `AT+CMGR=<index>` 的 `<index>` 是**当前 `<mem1>` 里**的序号 | 同上 |

于是 `+CMTI: "SM",7` 落在 `mem1="ME"` 的时候，直接下发 `AT+CMGR=7` 读到的是
**模组 FLASH 里第 7 格那条**，还把人家标成已读 —— 推送里出现的正文与真实新短信
毫无关系。实机读侧（`AT+CMGL=4`）之所以没这个问题，纯粹因为它**压根不指定区、
只读当前 mem1**。

正确形状（[urc.rs:209-260](../src/rust/src/urc.rs#L209)）：

```
+CMTI: "<mem>",<index>
   ↓ 若 <mem> 与当前 mem1 不同
AT+CPMS="<mem>","<mem>","<mem>"     -- 只认手册 8.1.3 承认的可写区名 SM / ME
   ↓ 等到 OK 且无 error，再 sleep CPMS_SWITCH_GAP(500ms)
AT+CMGR=<index>                     -- 单条预算 SMS_LIST_TIMEOUT(25s)
```

`AT+CPMS` 回 `OK` **只代表命令被接受，不代表介质已经换完** —— 这 500ms 的间隔与
`purge_all` 用的是同一个常量，来源是厂商 WebUI 在同一步上的实测等待。
切区失败不阻断：记一条 warn，仍按当前区读，把不确定性留在日志里而不是吞掉推送。
读回来的条目按 `(发件人, 参考号)` 做**跨条聚合**（`assemble_partial`），分段齐了才推送，
发件人号码在推送前归一成界面口径（`8613800138000` → `13800138000`）。

### 4.3 `AT+CMGR` 的另一半语义

`AT+CMGR=<index>` 同样会把该条从"未读"翻成"已读"（手册 9.10.2）。所以
**"+CMTI → CMGR" 这条路也不能用来维持未读状态**，与 §3.4 同源。

### 4.4 存储将满：`^SMMEMFULL`

模组主动上报，**可能出现在任何一次命令的应答中间**，所以读循环要把它当 URC 摘出去
（[atclient.rs:1234](../src/rust/src/atclient.rs#L1234)），而不是塞进那条命令的返回值里
当成 `+CMS ERROR`。判据是三种同义写法都算：`CMS ERROR: 322`／含 `MEMORY FULL`／
`^SMMEMFULL`（[urc.rs:536](../src/rust/src/urc.rs#L536)）。

后果分两条路：

- 走 URC 的：按通知配置发一条「存储将满」（`notify_memory_full` + `notify_tpl_memory`），
  与收到短信同一条推送通道；
- 走发送失败的：`send()` 拿到 `Rejected` 时用同一判据置 `mem_full` 标志
  （[sms.rs:532](../src/rust/src/sms.rs#L532)），随后 `capacity` 回包里带
  `memFull: true`（[rpcserver.rs:606](../src/rust/src/rpcserver.rs#L606)）供界面提示；
  下一次 `AT+CPMS?` 读到 `used < total` 就自动清掉（[sms.rs:768](../src/rust/src/sms.rs#L768)）
  —— 参考实现里这个标志置位后**永不复位**，用户清空后仍一直报"存储已满"。

**没有自动清理**：任何静默删用户短信的策略都不做。
另注：`^SMMEMFULL` 只在**恰好收满**的那一刻报一次，所以定时推送里的容量告警走的是
本地读数而不是这个上报（[urc.rs:648](../src/rust/src/urc.rs#L648)）。

## 5. 发送短信

### 5.1 收件人号码归一（编码前）

实机 `smssend.normalize()` 与本仓库 `normalize_destination()`
（[pdu.rs:706](../src/rust/src/pdu.rs#L706)）规则完全一致：

| 输入 | 处理 | 结果号码 | TOA |
|---|---|---|---|
| 任意 | 先剥掉 `\s` `-` `(` `)` | — | — |
| `+8613800138000` | 去 `+` | `8613800138000` | `91` 国际 |
| `008613800138000`（>8 位） | 去前导 `00` | `8613800138000` | `91` |
| `13800138000`（11 位且 `1` 开头） | 补国家码 | `8613800138000` | `91` |
| `8613800138000`（≥12 位且 `86` 开头） | 原样 | `8613800138000` | `91` |
| `10000`、`10086`、座机 | 原样 | `10000` | **`81` 国内** |
| 非全数字、位数不在 `2..20` | **拒绝** | — | `invalid destination number` |

`81` 这一路是关键：`pdul.lua` 把 TOA **硬编码成 `91`**，SMSC 会把 `10086` 读成
`+10086` 然后丢掉。所以 `smssend` 在编码完成后又补了一遍 `retarget()`，按上表把
PDU 里的 TOA 字节改回去 —— 偏移位置见 §5.4。

界面侧还有一层前置校验（实机 `action_smssend`）：`^%+?[%d%s%-()]+$`、`#number <= 32`、
`#text <= 2048`、不含 `\0`。**过不了这层的请求根本不会下发任何 AT。**

### 5.2 编码选择与容量

| | 本仓库 | 实机 `pdul.lua` |
|---|---|---|
| 单段上限 | GSM7 **160** septet／UCS2 **70** 字符 | 恒 UCS2，**60** 字符（`sendLimit = 60 * 4` = 240 个十六进制字符） |
| 多段每段 | GSM7 **153**／UCS2 **67**（UDH 从容量里扣掉） | UCS2 **60** 字符 + 6 字节 UDH 另算（`MSGLen = 正文/2 + 6`，长度字段随之变长，仍在 140 字节内 —— 只是比本仓库每段少 7 个字） |
| 判定 | 全文都在 GSM 03.38 基本表+扩展表内 → GSM7，否则 UCS2；不支持字符 → 报错而不是替换成 `?` | 恒 UCS2；`ord > 0xFFFF`（emoji，UTF-8 4 字节）在 `smssend` 里**预先拒绝** —— `pdul.lua` 的 UCS2 编码器只走 1–3 字节，遇到会返回 nil、一条 PDU 都不生成 |

`smssend` 的 `fix_udhi()` 补的是一个真实存在的编码器缺陷：`pdul.lua` 在
`len(MSG) >= sendLimit` 时置 UDHI 位，却只在 `> sendLimit` 时才写 UDH 头 ——
**正好等于上限的那一个长度**，PDU 声称有头而没有，接收方会吞掉正文头 6 字节。
本仓库不存在这个边界（`chunks` 的容量与 UDHI 置位用同一个常量）。

### 5.3 SMS-SUBMIT 首字节（TP-MTI 字段）

| bit | 字段 | 本仓库 | 实机 |
|---|---|---|---|
| 7 | TP-RP 回复路径 | 0 | 0 |
| 6 | **TP-UDHI** | 多段时 `0x40` | 多段时 `0x40` |
| 5 | **TP-SRR** 索要状态报告 | **`0x20`（恒置 1）** | 0 |
| 4:3 | TP-VPF 有效期格式 | `0x10` = `10` = **相对格式** | `00` = 不带 TP-VP |
| 2 | TP-RD 拒绝重复 | 0 | 0 |
| 1:0 | TP-MTI | `01` = SMS-SUBMIT | `01` |

> 位序按 TS 23.038 的 SMS-SUBMIT 表：`bit2` 才是 TP-RD（`0x04`），`0x20` 是 `bit5` 的
> TP-SRR。本仓库源码注释曾经把 `0x20` 写成"TP-RD"，已改正
> （[pdu.rs:1026](../src/rust/src/pdu.rs#L1026)）。**置 SRR=1 的实际后果是网络侧会
> 生成状态报告**，与 `CNMI=...,ds=2` 叠加后落盘并经 `+CDSI` 上报 —— 这是"存储比预期
> 快满"的一个可疑来源，见 §9。

### 5.4 PDU 布局与长度字段

```
<SCA 长度>(1) [<SMSC TOA><SMSC BCD>]        ← 长度为 0 表示"用卡里配的短信中心"
<TP-MTI>(1) <TP-MR>(1)
<DA 长度>(1) <DA TOA>(1) <DA BCD>((digits+1)/2)
<TP-PID>(1) <TP-DCS>(1) [<TP-VP>(1)] <TP-UDL>(1) <TP-UD>
```

- `AT+CMGS=<length>` 里的 `<length>` 是 **TPDU 字节数，不含前面的 SMSC 字段**
  （[pdu.rs:647](../src/rust/src/pdu.rs#L647)）。实机 `pdul.lua` 算的是同一件事：
  `7 + len(DA字段)/2 + len(UD hex)/2 - 2`。
- 半字节交换（swap semi-octet）+ 奇数位补 `F`；地址字节长度 = 号码位数向上取整到偶数 ÷2 + 1（TOA）。
- 地址字段偏移：SMSC 长度为 0 时，DA 的 TOA 落在 **hex 偏移 8**（`00|01|00|DAlen|`），
  `smssend.retarget()` 就是原地改这两个字符；长度前缀怎么改都算它，所以不用挪。
- **TP-VP**（TS 23.040 §9.2.3.12 的相对编码，**别按字面当小时数读**；本 AT 手册不含这张表）：

  | TP-VP | 有效期 |
  |---|---|
  | `0～143` | `(n+1)×5` 分钟 → 5 分钟 … 12 小时 |
  | `144～167` | `12 小时 + (n−143)×30` 分钟 → 12.5 小时 … **24 小时（167）** |
  | `168～196` | `(n−166)×1 天` → **48 小时（168）** … 30 天 |
  | `197～255` | `(n−192)×1 周` → 35 天 … 63 天 |

  本仓库默认 **`0xA7`（167）= 24 小时**，与厂商 WebUI 用的是同一个值。
  ⚠ 这一档在 167/168 边界上直接翻倍：`0xA8` 是 **2 天**，不是 24 小时 —— 早期注释把它
  读成 24 小时，是把「`12 小时 + (n−143)×30 分钟`」写成了「`(n−144)×30`」，又给
  168～196 编了一条不存在的「1 天 + (n−168) 小时」公式。相邻档连续性可以拿来自查：
  143→12h、144→12.5h、167→24h、168→48h、196→30 天、197→35 天。
  实机 `pdul.lua` **整个不带 TP-VP**（VPF=00，由 SMSC 用网络默认值，通常 24–72 小时）。

- **UDH（多段）**：`UDHL=05` + `IEI 00` + `IPL=03` + `<ref>` + `<total>` + `<seq>`，共 6 字节。
  - UCS2：UDH 按字节前置即可，`TP-UDL = 6 + 该段字节数`。
  - GSM7：**UDH 与正文共享同一条 LSB-first 比特流**，中间由 `align_to(7)` 补出规范要求的
    填充位；`TP-UDL` 计 **septet 总数**（含 UDH 的 7 个 septet 与填充）。少算那 1 个填充位
    会让整条长短信错位。
  - 实机 `pdul.lua` 的参考号是 `math.random(0,255)`（且每次调用都 `randomseed(os.time())`）；
    本仓库用单调时钟低字节 +1，只需在同一收件人的短窗口内不重。

### 5.5 下发形态：这是本模组最反直觉的一条

**MT5700M-CN 不实现 `>` 提示符的两段式握手。** 唯一被接受的形态是长度与 PDU 写在
同一行、中间夹**字面的 `\r`（反斜杠 + 字母 r 两个字符）**：

```
AT+CMGS=20\r0031000D91683108108300F00000A70570F95B5C06
```

（`probe` → `13800138000`：`00` 短信中心 + 20 字节 TPDU = 21 字节 hex，报 `20`。
长度语义见 §5.4：**不含 SMS 中心字段**。）

同一台 MT5700M-CN 的实测对照：

| 发的内容 | 模组反应 |
|---|---|
| `AT+CMGS=19` + **真 CR** + PDU + CR | 只回显命令本身，随后**静默**：无 `>`、无 `+CMGS:`、无 ERROR |
| `AT+CMGS=19` + **字面 `\r`** + PDU | 立即 `+CMGS: <mr>` + `OK` |

手册 9.14.5 的举例正是 `AT+CMGS=18\r0011…`，并注明"使用 SSCOM 工具时对应的 `\r`
应改为 `\\r`" —— 串口上要发的是反斜杠加字母 r，不是回车。

推论，也是最容易踩的工程坑：**`sms_tool_q`（以及走它的 `ubus call qmodem send_sms`、
NRadio APP）在这台模组上永远发不出去**，因为它等那个不会来的提示符。它只在
一次性形态失败后被当作兜底试一次。本仓库同理：**标准两段式（TS 27.005 §3.4.1，
等 `>` → 写 PDU → Ctrl-Z `0x1A`）只作回退，不作主路径。**

回退触发条件要卡死（[sms.rs:495](../src/rust/src/sms.rs#L495)）：

| 一次性形态的结果 | 是否重试两段式 | 理由 |
|---|---|---|
| `+CMGS:` / `OK` | — | 成功 |
| 本地 `ERROR` / `+CME ERROR` | **重试一次** | PDU 还没进网络侧，换形态不算重发 |
| `+CMS ERROR` | **不重试** | 网络侧已拒，重发就是发第二条 |
| 超时静默 | **不重试** | 结果不明，**可能已经发出去了** |

第一步没等到 `>` 就**不写 PDU** —— 那样会把 PDU 当成一条新命令，模组回 ERROR，
用户看到的是一次莫名其妙的失败；此时直接把第一步的应答报出去。

### 5.6 完整发送序列

```
（取得短信事务，排队上限 10s，总预算 60s）
AT+CMGF?                       2s
AT+CMGF=0                      2s     ← 请求没切模式也要确保 PDU 模式
AT+CSCA?                       2s     ← 只有请求没带中心号码才读
（编码：号码归一 → 选编码 → 分片 → 生成 TPDU）
AT+CMGS=<len>\r<PDU>          40s/片  ┐ 逐片，片预算 = min(40s, 事务剩余)
  … 最多 N 片                          ┘
（任一非"接受"的片 → 写 ESC(0x1B)，然后停止并交还通道）
```

**ESC 清态**（[sms.rs:558-570](../src/rust/src/sms.rs#L558)）不是可选的礼貌动作：
模组可能正卡在"等 PDU"的半开输入态，这时候紧跟着的 `AT+CPMS?` 会被当成 PDU 吞掉，
于是一次发送失败**连带把后面的读写一起拖死**。实机在每一片失败后都先写
`at("\x1b", 3)` 再继续用端口，本仓库对齐它。

中心号码这一路的取舍：本仓库把 `AT+CSCA?` 读到的值**编进 PDU 的 SMSC 字段**；
实机恒发 `00`（0 长度 = 用卡里配的）。两者在网络侧通常等价，但显式带上能让
"改过 SMSC 但模组没生效"这种故障在 PDU 层就被看出来。

### 5.7 应答怎么判

| 模组回的 | 判定 | 界面 |
|---|---|---|
| `+CMGS: <mr>`（后随 `OK`） | `Accepted`，`<mr>` 是 TP-MR 参考号 | 成功；实机 JSON 是 `{"ok":true,"number":…,"toa":"81","segments":1,"refs":[19]}` |
| `+CMS ERROR: <n>` | `Rejected`，网络侧原因 | 明确失败，可改内容/号码后重发 |
| `+CME ERROR: <n>` / 裸 `ERROR` | `Rejected`，本地原因（含 `memory full` → 顺带置存储满标志） | 明确失败 |
| 超时/无回话 | **`Unknown`** | *"第 x/y 段未收到模组确认。短信可能已发走，请勿重复点击"* |

多段取**最坏的一片**作整体结论：任一 `Unknown` → 整体 `Unknown`；任一 `Rejected` →
整体 `Rejected`。**已接受的片不回滚、不重发。**

### 5.8 实机与厂商 Web 页的一条隐含差异

厂商页面走 `ubus`/`sms_tool_q` 的那条老路（等 `>`）**在本模组上必然失败**；
`smssend` 是后补的绕行方案，注释直说是"给想要把短信发出去的调用方用的"。
所以读厂商代码时**不要把 `sms_tool_q` 的成功返回当成本模组的正常路径**。

## 6. 删除与清空

### 6.1 槽位从 0 开始

这条以前是悬案，实机代码给了答案：厂商页面把 `pdu_decoder` 报的槽位号原样交给
`AT+CMGD=<slot>`，**其中就包含 0**。所以任何"index 为 0 视为无效"的守卫，后果都是
**最老的那条短信永久删不掉**。本仓库已把序号类型改成 `Option<u32>`
（[sms.rs:93](../src/rust/src/sms.rs#L93)、[pdu.rs:536](../src/rust/src/pdu.rs#L536)），
0 是合法槽位，"解析不出序号"才是 `None`。

### 6.2 逐槽删除，且必须降序

```
AT+CMGD=<slot>          每槽一句，2s/句
```

| 点 | 依据 |
|---|---|
| **一条命令一个槽位** | 模组不收槽位列表；`AT+CMGD` 的 27.005 语法里根本没有列表 |
| **从大到小删** | 实机 `action_smsdel` 注释原话：*"免得剩下的槽位号在中途挪位"*。删除会使高位槽位前移，升序删到一半，后面的号可能已经指向别条短信 |
| 去重 | 同一会话的长短信有多个槽位，重复下发只会多一个 ERROR |

本仓库同样排序（[sms.rs:621](../src/rust/src/sms.rs#L621)），并按槽位逐条上报真实结果，
不猜"应该都成功"。前端把一次点击的槽位数按 **8 个一批**分批
（[sms_center.js:37](../htdocs/luci-static/resources/view/at-webserver/sms_center.js#L37)）：
每批仍是后端的一次事务，批与批之间重发/刷新，中途失败也照常刷新。

### 6.3 清空全部

`AT+CMGD=<n>,<delflag>` 的 delflag（27.005；手册 8.6.2/8.6.3 同）：

| delflag | 语义 |
|---|---|
| 0 | 只删 `<index>` 指定的那一条（本仓库逐槽删除走这条） |
| 1/2/3 | 按状态删那一条（已读／未读／已读或未读） |
| **4** | **删除首选存储器（`<mem1>`）里的全部**短信（含未读）。且 **`delflag ≠ 0` 时 MT 忽略 `<index>`** |

于是两条实现都只是"清当前区"：

```
实机：   AT+CMGD=0,4                # 一条，当前 mem1
本仓库： AT+CPMS="<m>","<m>","<m>"   # 逐区
         sleep 500ms                 # CPMS 回 OK ≠ 介质已换完
         AT+CMGD=1,4                 # 那个 1 只是占位（delflag≠0 时被忽略）
         …下一个区…
         AT+CPMS="<原 mem1>","<原 mem2>","<原 mem3>"   # 还回去
```

`mem1` 决定之后 `list`／`delete`／`CMGR` 落在哪个区（手册 8.1.1），所以
**"清空短信"这一个动作不该连带改掉用户之后所有读写的默认介质** —— 这就是最后那条
还原命令存在的全部理由（[sms.rs:731-745](../src/rust/src/sms.rs#L731)）。
实机压根不切区，所以它没有这个副作用。
区名清单来自 `AT+CPMS?` 的真实回读；读不到时兜底只试手册 8.1.3 承认的 `SM`／`ME`，
对回读到的未知区名不猜测、只如实显示。

### 6.4 容量

```
AT+CPMS?
+CPMS: "SM",12,50,"SM",12,50,"SM",12,50
       └mem1┘ └used,total┘
```

实机取**第一个三元组**（`%+CPMS:%s*"[^"]*",(%d+),(%d+)`）；本仓库同样以 mem1 为准，
并把三个区的名字都留着用于换区循环。厂商 Web 页注释里记了一条实测现象：
**`AT+CPMS?` 偶尔会输掉串口竞争**，那一轮就读不到容量 —— 它选择保留上一次的读数，
而不是把容量条画成 0（读不到容量不算失败，列表照常显示）。

## 8. 超时预算（三层必须对齐）

后端先出结论、中间层略宽、前端最宽 —— 反过来就会出现"后端还在删、前端已经掐断 `nc`"，
而**掐断那一次还会打开「后端不可用」的共享熔断，连别的页面一起 15s 内全部快速失败**。

| 动作 | 后端预算 | ucode (`SMS_ACTION_TIMEOUT`) | 前端 (`SMS_ACTION_TIMEOUT_MS`) |
|---|---|---|---|
| `send` | 排队 10s + 总预算 60s（单片 40s） | 70s | 72000 |
| `purge` | 排队 10s + 逐区（切区 500ms + 25s） | 70s | 72000 |
| `delete` | 排队 10s + 每槽 2s + 回读 2s（前端限 8 槽/批）≈ 28s | **40s**（以前缺项，走默认 12s → 删两条分段短信必被切断） | **42000** |
| `list` / 存储类 | 排队 10s + 列表 25s | 40s | 42000 |
| `power` | CEUS/CFUN/IMS 全套 + 射频恢复 | 70s | 72000 |

关键常量位置：
[atclient.rs:20](../src/rust/src/atclient.rs#L20)（`COMMAND_TIMEOUT` 2s）、
[atclient.rs:32](../src/rust/src/atclient.rs#L32)（`SMS_SUBMIT_TIMEOUT` 40s）、
[atclient.rs:38](../src/rust/src/atclient.rs#L38)（`SMS_LIST_TIMEOUT` 25s）、

## 9. 待真机确认

以下四条**不能**靠读代码或跑 mock 定论，需要上真模组逐项验证：

1. **`CEUS` 的方向**：本插件开启短信时写 `CEUS=1`（数据中心），厂商 WebUI 写 `CEUS=0`
   且时机在 `CFUN=0` 之后。手册没有把 `CEUS` 与短信/IMS 绑定。验证办法：分别按两种
   取值走完整开启序列，再各发一条 `102 → 10000` 看能否送达。
2. **`AT+CFUN=0/1` 是否足以让 `CEUS` 生效**：手册 3.15.2 只说"需要开关机生效"，
   没承诺射频重启等价于开关机。
3. **TP-SRR=1 的后果**：置了状态报告请求，网络侧是否会因此往 MT 里写状态报告、
   并加速 `^SMMEMFULL`。若确认有害，把首字节从 `0x31` 降到 `0x11`（对齐厂商的 `0x01`
   则连 TP-VP 也要去掉）。
4. **半开输入态与 ESC**：`AT+CMGS` 超时静默后，ESC(0x1B) 是否真的能清掉模组的 PDU
   输入态（本仓库与实机都按"能"实现，缺一次仪器级观察）。
5. **跨区 `+CMTI` 的真实频率**：`+CMTI` 报的区与当前 `mem1` 不一致的情况在现网
   有多常见 —— §4.2 的修复在没有真机样本的情况下无法验证其覆盖面。

## 10. 手工复现（串口上怎么一条一条打）

工具：`/usr/bin/sendat`（实机自带，端口自动探测 + flock）。**只允许向 `10000` 发 `102`。**

```sh
# 0) 能力与参数
sendat 1 'AT+CPMS?' 5
sendat 1 'AT+CMGF?' 3
sendat 1 'AT+CMGF=0' 3
sendat 1 'AT+CNMI?' 3
sendat 1 'AT+CNMI=2,1,0,2,0' 3
sendat 1 'AT+CSCA?' 3

# 1) 读列表（注意：这一步会把未读翻成已读）
sendat 1 'AT+CMGL=4' 20 | pdu_decoder --json

# 2) 发一条（内容固定为 102，收件人固定为 10000）
#    走封装好的工具，它内部就是 AT+CMGF=0 + 单行 AT+CMGS
smssend 10000 102
#    只想看编码结果、完全不碰串口：
smssend --dry 10000 102
#    → {"ok":true,"number":"10000","toa":"81","segments":1,"pdu":["..."]}

# 3) 手工下发同一条（把 --dry 出来的 pdu 直接接在字面 \r 后面）
sendat 1 'AT+CMGS=14\r00310005810100F00000A70331980C' 40
#    期望：+CMGS: <mr> 然后 OK

# 4) 删一条（0 号槽是合法的）
sendat 1 'AT+CMGD=0' 10
sendat 1 'AT+CMGL=4' 20 | pdu_decoder --list      # 复查

# 5) 清空当前区
sendat 1 'AT+CMGD=0,4' 30
```

### 本文用到的、已核对过的报文

下表每一条都由 `pdu::build_submit_parts()` 生成、再由 `pdu::decode_*` 回读验证，
**长度与内容自洽**（`AT+CMGS=<length>` 的 `<length>` 恒等于 PDU 去掉 SMSC 字段后的字节数，
即 hex 长度 ÷ 2 − SMSC 字段字节数）。收件人统一取文档示例号，短信中心统一写 `00`
（长度 0 = 用卡里配的），因此这些报文里没有任何指向真实网关的地址。

| 场景 | `AT+CMGS` 那一行（多段以 `…` 截断） |
|---|---|
| `102` → `10000`（GSM7，TOA 81，1 片） | `AT+CMGS=14\r00310005810100F00000A70331980C` |
| `你好` → `13800138000`（UCS2，补 `86`、TOA 91，1 片） | `AT+CMGS=19\r0031000D91683108108300F00008A7044F60597D` |
| 160 个 `A`（GSM7，恰好单片上限，1 片） | `AT+CMGS=155\r0031000D91683108108300F00000A7A0C16030180C0683…`（UDL `0xA0`=160 septet） |
| 161 个 `A`（GSM7，2 片，参考号 `0x85`） | 片 1 `AT+CMGS=155\r0071000D91683108108300F00000A7A005000385020182C16030180C…`；片 2 `AT+CMGS=29\r0071000D91683108108300F00000A70F05000385020282C16030180C0601` |
| 80 个 `测`（UCS2，2 片，参考号 `0x85`） | 片 1 `AT+CMGS=155\r0071000D91683108108300F00008A78C0500038502016D4B…`；片 2 `AT+CMGS=47\r0071000D91683108108300F00008A7200500038502026D4B…` |

字段读法示例（第一条）：`00` SMSC 长度 0（用卡里配的）· `31` SMS-SUBMIT + 相对有效期 +
SRR · `00` TP-MR 由模组填 · `05` 地址 5 位数字 · `81` TOA 国内 · `0100F0` 半字节交换的
`10000`（补 F）· `00` TP-PID · `00` DCS=GSM7 · `A7` TP-VP=24 小时 · `03` TP-UDL=3 septet ·
`31980C` = `102` 的 7bit 打包。

`<length>` 怎么数（最容易写歪的一格）：表中的 PDU 形如
`00 | 31 | 00 | 0D 91 68… | 00 | 08 | A7 | 04 | …`，开头的 `00` 是 SMSC **长度字节**，
所以 `AT+CMGS` 报的是 `PDU hex 长度 ÷ 2 − 1`。`102` 那条 15 字节 → `14`；
`你好` 那条 20 字节 → `19`；160 个 `A` 那条 156 字节 → `155`，UDL `0xA0`=160 septet 恰好填满
140 字节用户数据；161 个 `A` 多出来的那 1 个字符触发分片，片 1 的 UDL 变成
`7 个 septet 的 UDH + 153 个正文 = 0xA0`，于是仍是 `155`，片 2 只有 `153…161` 这 9 个字符
（`29` 字节 TPDU → `AT+CMGS=29`）。

多段那两行的差异只在首字节 `71`（多出 bit6 的 TP-UDHI）与 UDH：`05 00 03 85 02 01`
= UDHL 5 · IEI `00`（8 位参考号）· 长度 3 · 参考号 `0x85` · 共 2 段 · 第 1 段。
GSM7 那一行的 `TP-UDL=0xA0`（160 septet）= UDH 的 7 个 septet（含 `align_to(7)` 补出的
1 个填充位）+ 正文 153；UCS2 那一行的 `0x8C`（140 字节）= 6 字节 UDH + 67 个字符。

> **合成样本，不是实机报文**：本表与全文所有 PDU 都是编码器现算出来的，
> 收件人是 `13800138000` 这类文档示例号、短信中心一律 `00`。
> 真机只向 `10000` 发过内容 `102`（见文首「测试边界」），
> 实机日志里出现的真实短信中心地址不收录进文档。
