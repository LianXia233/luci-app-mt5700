## 一句话结论

**两个参考项目的 eSIM 能力面，本项目基本都已经有了，而且有几处比它们更深**（二维码录入、CSIM 256 字节上限的系统性规避、超时后不敲门、零第三方二进制）。

按收益 ÷ 成本筛完，值得动的只有 **4 项**：

- ✅ **建议做**：① 切卡后身份收敛校验（**直接命中本项目已发生过的事故**——红线 24：旧卡身份带给新卡）、④ SW 91xx 进错误矩阵（顺手 10 分钟）
- ⚠️ **可做但不急**：② 下载前空间预检（低频保险）、③ 切卡前作废缓存身份（与 ① 同源，必须捆绑做，别单独立项）

其余差异要么本设备不适用，要么与既有红线冲突（CFUN 重载会挂死 eth2、QMI/MBIM 是 Quectel 专属、多 eUICC AID / CardPolicy 是死代码），**明确不建议搬**。
详见第零节的价值判定表。

## 零、价值判定（先回答「值不值得做」）

对照的**目的不是对齐功能清单**，而是找「本项目真会踩到的坑」。两个参考项目都是 Quectel 平台、面向多设备池化管理的服务端，
业务前提（多卡槽轮换、VoWiFi、QMI/MBIM 传输）与本项目的单卡槽 5G CPE 差别很大 —— 逐条搬只会导致死代码（红线 14）。
下面按「收益 ÷ 成本」给判定，**只有 1 条是建议尽快做，2 条看排期，其余明确不做**。

## 二、建议补全（按优先级）

### ① 切卡后的「身份收敛校验」—— 最高优先级

**参考**：VoHive `shouldForcePostSwitchSIMReload`（`pool_esim_switch.go:2448`）先用 `GetICCIDLive`（3s 超时）探测，**目标 ICCID 已生效就跳过重载**；
`refreshPostSwitchIdentityWithPolling`（`:379`）在生效后还要**等 IMSI 也非空**才收工，注释写明理由：

> `// ICCID 已生效，但 IMSI 可能仍在 USIM 重初始化窗口中。为避免把空 IMSI 持久化，等到 IMSI 也成功读出再退出。（:429-430）`

**本项目现状**：`pollListAfterToggle()`（`esim.js:1408-1439`）是**固定退避**（`backoff = [6000, 12000, 24000]`，封顶 3 次）轮询 **Profile 列表**：

```js
Euicc.listProfiles(send).then(function (res) {
    busy = false;
    renderTable(listCard, res.list || []);   // ← 列表读成功即收工
    showPendingReceipts();
})
```

全程**从不校验「当前实际生效的是不是目标那张卡」**；失败路径也只是 `appendChild('卡片刷新中，请稍后点击「刷新列表」')`。

**为什么这条最要紧**：项目红线 24 记的就是这类事故——**旧卡身份被带给新卡**（曾把旧卡 EID 带给新卡）。
列表刷新成功 ≠ 身份已切换；在重注册窗口里读到的很可能是旧值，下游页面会拿错身份。

**落地思路（纯逻辑，无新 AT 语义）**：切换成功后，把「列表轮询」升级为「目标 ICCID 收敛确认」：
轮询时同时取当前生效身份，与目标 ICCID 归一化比较（项目已有 `Euicc.normalizeIccid` / `iccidKey`），
**命中才收工并刷新列表**；超时未命中则明确提示"卡片仍在重注册，当前生效的可能还是旧卡"，而不是笼统的"卡片刷新中"。
有 IMSI 可读时，同样等非空再收工（对齐 VoHive 那条注释的理由）。

**风险**：低。不改任何下发指令，只改轮询的终止条件与提示文案。

---

### ② 下载前的空间预检

**参考**：VoHive 在 `DownloadProfile` 里拦截（`manager.go:3572`，并有独立错误码 `euicc_insufficient_memory` `download_error.go:12`）：

```go
if checkInfo.FreeNvramBytes > 0 && checkInfo.FreeNvramBytes < 81920 {   // manager.go:3572
```

注意它带了 **`> 0` 前置守卫** —— 读不到容量就不拦。这正是本项目红线 23「无差别兜底会把『读不出来』伪装成『没有』」的同构做法，值得照抄这个守卫形态。
VoCat 则用 NVRAM 前后差值驱动预检与回显（`esim_download.go:61`，`SpaceDelta`）。

**本项目现状**：`esim.js:1233-1237` 把 `freeNonVolatileMemory / freeVolatileMemory` 展示得很清楚（`:370` 还注明了"SGP.22 只定义剩余，不做百分比"，这点比两家都严谨），
但**下载流程 `runDownload()`（`esim.js:919`）完全没用这个数** —— 空间不足要等到写卡中途才炸，且用户已经等了几百个块的写入进度。

**落地思路**：开始下载前读一次 EUICCInfo2，剩余非易失存储低于阈值就先拦截并说明（阈值建议先用运营商常见包体积估，别照抄 81920 —— 那是对他们卡型取的）。
读不到容量时按"无法预检"放行并说明，不做硬拦（避免把"读不到"误判成"空间不足"，这是本项目一贯的兜底原则）。

**风险**：低。复用已有解析，不下发新指令。

---

### ③ 切卡前主动作废缓存身份

**参考**：VoHive `handleESIMSwitchBefore`（`pool_esim_switch.go:356`）：

> `// 切卡前主动清空 DeviceSnapshot 中缓存的 ICCID/IMSI，防止切卡后其他代码路径从 Snapshot 读到旧卡身份。`

**本项目现状**：切换后的刷新做了，切换**前/期间**没有作废动作，重注册窗口内其它页面（网络状态等）仍可能读到旧身份。
与 ① 同源，都是红线 24 那一类。

**落地思路**：进入切换流程即置"身份待定"态，期间任何读身份的路径返回"切换中"而非旧值；切换收敛（① 完成）后再恢复。

**风险**：中低。要动到跨页面共享的身份取数，改动面比 ①② 大，建议与 ① 一起做、一起验。

---

### ④ 小修：SW 91xx 未进错误矩阵

**参考**：VoCat `es10StatusOK`（`esim_lpa.go:65-69`）明确注释——`91xx` 是**成功但有待处理的 proactive SIM Toolkit 命令（refresh）**，需要复位卡片来应用 refresh，不是失败。

**本项目现状**：业务路径确实写了三处放行（`if (r.sw !== '9000' && r.sw !== '9100')`，`euicc.js:2382,2417,2625`），
而 `api.swInfo()`（`:379`）没有 91xx 分支。

> **★ 2026-09-24 更正（会审推翻，本条原判「极低风险、纯展示层」是错的）**
> 那三处放行判据**根本执行不到**。`sendApdu` 的唯一实现是 `euicc.js:878` 起的 `sendAndCollect`，
> 它在 `:964/:967` 先过 `swInfo`，凡 `level` 为 `error|fatal` 一律抛；`9100` 没有分支 →
> 掉到 `:521-525` 的兜底 `level:'error'` → **在进入业务层之前就抛了**。
> 三处 `!== '9100'` 因此是死代码。真实定级是 **P0 功能缺陷**（卡回「成功带 refresh」时整条链路报错），
> 不是展示层文案优化。
>
> 已于 2.3.44 修复：补 9xxx 分支（不只 `9[01]`，避误杀其余合法 9xxx），`91xx` 单独挂 `refreshPending`；
> 同时给 `runOperation`（`:1664`）补上原先完全缺失的 SW 检查（它此前只看 ES10 结果码）。
> 防回归：4 条契约断言 + `tools/verify-guards.py` 一条变异用例。

## 三、明确**不建议**搬的（含红线冲突）

| 参考项目做法 | 不搬的理由 |
|---|---|
| VoHive 切卡后强制 SIM 重载：`AT+CFUN=4` → `AT+CFUN=1`（`pool_esim_switch.go:2396-2424`） | **红线 15：`CFUN=0/1` 会挂死 eth2**。而且 VoHive 自己也有前置判断尽量跳过，本项目网络口就是命脉，更不能碰 |
| VoHive 的 QMI / MBIM 传输通道、`QMIErrCardCallControlRefFail(0x0030)` 卡复位语义 | Quectel 专属，本模组不适用 |
| VoCat 的 PC/SC、QMI 双通路 + 多 eUICC AID 发现（`discoverEuiccAIDs:493`） | 单卡槽 CPE，无多 AID 场景；做了就是死代码（红线 14：只留适配本设备的功能） |
| VoCat 的 CardPolicy（按 ICCID 存 VoWiFi / 飞行模式策略） | 鼎桥 5G CPE 无 VoWiFi，且本项目已有飞行模式页，重复建设 |
| VoHive 的"disable 接口" | 它自己是**半成品**：后端实现了但路由表没有端点、前端 `v-if="p.state !== 1"` 使禁用分支不可达（`manager.go:2683` / `DeviceEsimTab.vue:630`）。是反例，不是榜样 |
| VoHive 大量 TLV 解析 panic recover 兜底 | 那是 Go 侧 euicc-go 解非标 TLV 会 panic；本项目是 JS，解析早已用 `EUICC_TLV_TRUNCATED` 显式守卫，不需要照抄 recover 模式 |

## 四、本项目的优势（别在"对齐参考项目"时改掉）

1. **二维码录入**：扫摄像头 / 上传图片 / 拖放 / 粘贴 / 手动填 SM-DP+ 四条路，且用内置 jsQR 兜底 `BarcodeDetector`（后者只在安全上下文可用）。
   VoHive **明确没有二维码**（`DeviceEsimTab.vue` 只有五个文本框）；VoCat 也只有文本表单。
2. **CSIM 256 字节上限的系统性规避**：取 Profile 请求**故意只放 5 个 tag**（`euicc.js:611`，注释写明"上限 5 个，保证响应 <256 字节规避 61xx"），
   VoCat 靠 mss=120 分块，VoHive 无此约束。本项目还额外排除了 icon tag（与 VoHive `basicProfileTags` 排除 icon 的思路一致，但本项目是默认就这么做的）。
3. **超时后不敲门**：`euicc.js:1029` 一整段注释记录真机事故——卡还在算的时候补发 GET RESPONSE 会被拒成 `CME ERROR: Incorrect parameters`，
   把"丢一个回执"升级成"整包作废"。正确做法是连发普通 AT 把迟到回包接回来。两家中都无对应经验。
4. **通道泄漏检测**（`euicc.js:1406`）：记录通道号变化并提示，避免累积到第 20 次后 open 失败。
5. **策略禁止删除有独立错误码** `EUICC_POLICY_DENIED`（`:829`），比 VoHive 只有前端文案更规整。
6. **零第三方二进制**：ES9+ 链路自研，不需要 euicc-go / lpac。两家分别依赖 euicc-go 与"对齐 lpac 字节级格式"。

## 五、可选讨论项（不算缺口）

- **通知失败的分级**：VoHive 把"操作成功但通知发送失败"降级为 **Warning + warningCode**，操作本身仍算成功（`manager.go:3032-3059`）；
  本项目是"装上但回执没发出 → 红色横幅"（`esim.js:1006-1014`）。
  本项目更保守、更醒目；VoHive 更贴近"操作确实成功了"的语义。这是取舍不是对错，**建议保持现状**——对 CPE 用户来说，回执没发出是必须知道的。

# 附录：VoWiFi「零信号通信」与「私有代理池」的判定

> 这两块与 eSIM 不同 —— 用户明确说过「VoWiFi 我想要能实现一定要实现」，
> 所以不能只写「不做」。下面给出**手册取证 + 架构论证**，以及**能落地的替代方案**。
> AT 指令一律以《MT5700M-CN AT 命令手册》V200R001C20（238 条）为准，Quectel 命令不照搬。

## A. 真 VoWiFi（ePDG / IKEv2 / WLAN 承载切换）—— 不可实现

三层独立取证，任一层都是否定：

1. **手册层：零可配命令**。全手册 grep `ePDG|IWLAN|VoWiFi` 只命中**错误原因码**，
   没有任何 ePDG 地址配置、WLAN 承载切换、VoWiFi 开关命令：
   - `appendix_20_5_TAF_CS_Cause列表.md:1471`（VOWIFI 呼叫掉话）
   - `appendix_20_4_TAF_PS_Cause列表.md:1621-1831`（「WLAN 下 PDP 激活 IKED 异常」一系列）
   → 结论：固件**内部**确实有 IKED / WLAN PDN 概念，但**没有对外配置接口**，
   也就是「看得见、够不着」。
2. **架构层：方向自毁**。VoWiFi 的前提是 UE 用 **WLAN 侧接入**去建运营商 IMS 隧道。
   本设备的 WiFi 是它**自己发出的 AP**（下行 LAN），蜂窝是**唯一 WAN 上行** ——
   「零信号」时根本不存在任何可用出口，用自己发出的 WiFi 承载自己的 IMS 等于自己绕自己。
   固件里的 IKED 只能在蜂窝**已注册**时做补充承载，无法独立成通道。
3. **业务层**：即便固件支持，也需 HSS 开户 + ISIM 内 EF 配置（ePDG 地址、IMS 参数），
   这不是 AT 能配的。

**结论：不引入 ePDG / IKEv2 / EAP-AKA / 8 态状态机。**

## B. 能落地的替代：IMS 能力可视化 + 开关生效校验（已随 2.3.44 落地）

真 VoWiFi 不可实现，但用户诉求背后**可落地、且手册有据**的部分是 IMS —— 手册里确实有：

| 命令 | 作用 | 手册位置 |
|---|---|---|
| `AT^IMSSWITCH=<lte>[,<utran>][,<gsm>]` | IMS 业务能力开关，**掉电保存 Y / PIN N**；三条失败条件：存在 IMS 业务 / PS_ONLY 下关 LTE 域 / 协议栈切换失败 | `commands/4 呼叫控制命令.md:595-650` |
| `AT+CIREG?` → `<n>,<reg_info>[,<ext_info>]` | IMS 注册状态 + **IMS 域能力值**（voice / text / SMS over IMS / video） | `commands/7 UMTS分组域命令.md:678-740` |
| `AT+CGSMS` | 短信承载域（CS/PS 选择） | 手册 7.7 |
| `AT+CEUS` | 语音中心 / 数据中心 | `commands/3 配置命令.md:995` |

本项目**原本已有** `^IMSSWITCH` 开关与短信序列，所以缺口不在"有没有开关"，而在**谎报**：

- `parseCireg` 丢弃 `ext_info` → 页面仅凭 `reg_info===1` 就宣称「VoLTE/VoNR/IMS 短信可用」，
  而「注册上了但能力值里没有 voice」这一最常见故障态会被报成可用；
  反向地，固件回十六进制时 `Number()` 得 NaN，又被判成「语音/IMS 短信不可用」。
- `^IMSSWITCH` 写后**不回读**，而它是掉电保存命令且有三条失败条件 → 没生效的写入会被报成成功。

两者已在 2.3.44 修掉（详见 CHANGELOG）。**注意**：`ext_info` 只**原样透出、不做位解码** ——
手册同一节既说「每个 bit 位表示不同的能力」又按枚举方式列举取值，口径本身不一致，
没有真机实测前解码就是编造。是否需 `AT+CIREG=2`（写命令）待真机只读实测，**不静默下发**。

## C. 私有代理池 —— 拆分三段裁决

用户明确了诉求的真实含义：**私有代理池 = 通过多卡切换实现 IP 切换**（不是 VoCat/VoHive 那套
SOCKS 导出 / 按国家 MCC 分流形态）。按这个口径拆三段：

| 段 | 裁决 | 理由 |
|---|---|---|
| **参考项目那套形态**（`exportproxy` 的 SO_MARK + SO_BINDTODEVICE 绑网卡；`upstream_proxy` 按国家/MCC 四层分流） | **不做** | 绑网卡的前提是多 WAN 网卡（本机唯一上行是蜂窝）；按 MCC 分流的前提是池里有 N 张卡（本机 MCC 恒定）→ 100% 死代码（红线 14） |
| **Profile 级轮换**（eUICC 上多个 Profile 之间切换 → 出口 IP 轮换） | **做，但排在 A/B 之后，且需先拿到实测** | 所需能力已全部存在（`toggleProfile` + 确认弹窗 + 收敛轮询），缺的只是编排层 |
| **卡槽级自动轮换** | **明确禁止** | 走 `AT^HVSST` + `AT^SCICHG` + `AT+CFUN=0/1`：高危 AT（红线 15 禁测）、会整段断网（红线 39 须征得同意），且切到**空槽**会让唯一上行永久离线 —— 远程就救不回来了 |

### ★ 关键前置：「换 Profile ⇒ IP 变」—— 2.3.44 时是零证据，2.3.45 已补齐判定手段

> **★ 2026-09-24 更正（本条原判「零证据 → 只交付观测」，现已被推翻）**

原判没错的一半是：**当时**全仓确实没有任何出口 IP 探测手段，而运营商 CGNAT 下同一 APN
地址池完全可能复用同一个地址，所以在未验证的假设上动工自动轮换是不对的。

错的一半是：我把「当时没有手段」当成了「这件事在本机上做不到」，于是只交付了观测。
**这个推论不成立** —— 对照 vohive 的做法（`internal/netprobe/netprobe.go`），取公网出口 IP
根本不需要模组配合：从设备侧发一次 HTTP 回显、看对端认到的源地址即可。它用的
`SO_BINDTODEVICE` 绑网卡，在 OpenWrt 上就是 `curl --interface`（本项目红线 37 里已有现成模式）。

所以 2.3.45 补齐了这个原语：

- 新增后端 `mt5700.exitip`（三个写死的 http 回显端点，不接受外部传入 URL），并放行 ACL；
- 新增前端 `Parse.parseExitIpBody` 做严格校验（错误页 / 越界段一律判「没取到」，不给占位值）；
- eSIM 页原「数据承载 IP 观测」卡升级为「换卡换出口 IP（实测）」卡：
  同时记**承载地址**（`AT+CGPADDR`）与**出口 IP**，并给出三选一结论 ——
  已变 / 未变 / **无法判定**（最后一支是独立的，不许把「读不出来」说成「没变」）；
- 补「切换未确认生效 → 一键切回原 Profile」，但**不做自动回滚**（理由见 CHANGELOG 2.3.45）。

**仍然不做的**（与上面的补齐无关，是架构约束，不是能力缺失）：

| 项 | 为什么不做 |
|---|---|
| 定时自动轮换 | 单模组 + 蜂窝是唯一上行，定时切换 = 定时断网 |
| 卡槽级热切换（`^HVSST`/`^SCICHG`/`CFUN`） | 高危 + 空卡槽会永久废掉唯一上行 |
| SOCKS/HTTP 代理导出 | 单上行时代理出口 IP 与 NAT 出口 IP 是同一个，纯死代码（红线 14） |
| **多模组池**（vohive 的 `Pool` 本体：N 个 Worker 各带一个 modem，轮换＝换 Worker） | **硬件只有 1 个模组**。它们的「池」是**模组的池**，这一维在本机上不存在 |

> 最后一行才是「它们能做、这台设备做不到」的**唯一**真实差异；其余各项要么已补齐，
> 要么是不该做，不是做不到。

**下一步（需人工一次性试验）**：手动启用另一个 Profile → 看「换卡换出口 IP（实测）」卡给出的结论。
出口 IP 变了 → 轮换池值得建；没变 → 该环境下此路不通（结论由卡片直接给出，不用推理）。
